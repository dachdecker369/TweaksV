## How the work runs

Three levels, as my rules for every project have them:

- **The overview** (the overview) reads this plan and the findings it names, reads the weekly limits and starts the merge. It checks the findings before anything is built on them, checks the merged main from its diff, asks for my boots, reads them, tags 2.6.0 and pushes. It is the only track I talk with.
- **The merge** (the merge) makes the scaffold on main first (D11), then turns this plan into one plan per track and starts the tracks in its track, the coding tracks and the research pass side by side. While the round runs it alone commits to main and keeps the local notes; it verifies each coding track from its branch, rebases the tracks onto main in the order of the table, makes the documents one, sets the version, rebuilds from clean, runs the suites and reports the build up.
the ninth, the ray tracing buffer's coding track, starts once the overview has checked the research's findings (D16). None merges, tags, pushes or sets the version.

Each coding track commits on its branch only, each item its own commit. After every commit it writes its state into its paragraph of the Next steps and into its local notes and reports in two lines, without stopping; it ends its turn only when its track is done or a decision of mine blocks everything left. The research pass commits nothing: it keeps its findings file in my research tools' folder and its state in that file's State section, written after every step, and reports the same way. No committed file and no commit message names a local folder or a branch: a track's paragraph says "on a branch of its own". Before every push the net diff, every commit's own diff and the messages are searched, as my rules have it.

A coding track writes where it stands into its local notes before each item and before every step that may run long, and from 70% of its context on at every sub-step - the files touched, what is done of the item, what is next - and never holds more than one item's work uncommitted; by message it sends the merge only a two-line report per commit and its blocking questions, everything else going into its paragraph of the Next steps and its notes file, `<suite>-to-merge.md` in the notes folder. The merge writes the State and its local notes after every step and before every step that may run long - the tracks started, each report, each verification's verdict, each rebase and fast-forward, every open question; each track's id beside its title stands in the local notes alone, since this file is pushed and names tracks by their titles - and commits them with its next commit or on their own; it verifies each track's branch, which appends every finding to a file in the scratchpad and answers in 300 words at most, spot-checks what matters most itself, and reads rebase conflicts and build logs filtered, never whole. It messages the overview only for a question or an approval of mine, a track stuck, and the build ready - every other milestone goes into `merge-to-overview.md` in the notes folder - and nudges a track that a usage window or an error stopped, once the window has reset.

Every coding track builds from its findings file in my research tools' folder, `C:\_DEVELOPMENT\_Tools\TweaksV-research\output-1158.16\<topic>_findings_for_the_clean_room_build.txt` - the design (section 8) and the hand-over (the last section: the patterns with their offsets, what each match holds, the facts no pattern protects) - with the decisions below where they change the design (D12), from phase A's module of its limit, which it turns into the part, and from the review beside the findings, `<topic>_review.md`; the static bounds track builds from the original's source (D15), the Legacy packs track from D17. No track reads code of an original whose license does not allow it (D2) - Resource Extensions' plugin least of all - and only the research pass analyses the dump (D16): a fact a coding track's findings lack goes up as a question.
