# Specifications

The design of TweaksV as it is built: every module of the source, what it does, what it checks, what it writes and what it logs, so that the source can be understood, forked or built on without opening it. Four files carry the whole truth about TweaksV, each with its own job:

| File | Carries |
|---|---|
| [README.md](README.md) | the player's view: what each part does, every key of `TweaksV.ini`, building, testing, other mods |
| SPECIFICATIONS.md, this file | the design: the files, the tables, the start-up, the formats, the shared code, the mechanism of every part, the rules, the tests, how to extend it |
| [PATTERNS.md](PATTERNS.md) | the game facts: every byte pattern, what the match holds, where it matched on the current build, how the sites are encoded |
| [NOTES.md](NOTES.md) | what each part does with the checks it makes, the measurements, the open issues, the bugs found in the projects the parts derive from |

Credits and derivations are in [CREDITS.md](CREDITS.md), the notices in [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md). [SECURITY.md](SECURITY.md) says how to report a security problem and what it covers; [ROADMAP.md](ROADMAP.md) holds what I plan next and [PLAN.md](PLAN.md) the phases of a change while one is under way, a placeholder while none is. ## 1. What TweaksV is

One ASI plugin for GTA V Enhanced, `TweaksV.asi`, loaded by an ASI loader into `GTA5_Enhanced.exe`. It does nothing in any other program. Fourteen parts change the running game in memory, never a file on disk: the heap size (HeapAdjuster), the modkit array (ModkitLimit), the packfile array and the archive count of the game's configuration (PackfileLimit), the box streamer's traversal list (BoxStreamer), the decal definitions array (Decals), a mods folder with unencrypted archives, whose packs it checks for GTA V Legacy, and the cache check (RageOpenV), the three start-up screens (StraightToStoryMode), the files DirectStorage keeps locked (DirectStorage), the threshold up to which the game's own script makes the vanilla blips (Blips), the room for `weapons.meta` files and for weapon component definitions, each with its guard (WeaponLimits), the props per anchor of a ped model (PedProps), the video memory budget for streamed textures and buffers (Resources), the static bounds pool's size (StaticBounds) and the ray tracing buffer of moving geometry (RayTracing). Every part but DirectStorage, which hooks two functions of Windows and needs no pattern, finds the game's code by byte patterns, checks every site before it writes, writes all of its sites in one go or none, leaves alone what another mod has already changed, and says in the log and in one start-up message box what it could not do. With `DIAGNOSTIC_MODE=1` the parts that have a measurement also measure how the game uses what they change, and TweaksV measures the two limits of a part to come before it changes the game - the siren setting IDs and the sirens per vehicle (SirenSettings) - and writes nothing for them but one redirected call of the siren count's measurement (section 11.15).

Everything is driven by three tables - the settings, the patterns, the parts - and by shared services: the log, the start-up summary, the scanner, the patch module, the relocation core. A new part is an entry in each table plus one file of its own.

Conventions every `.cpp` and `.h` follows: the first line is `// SPDX-License-Identifier: GPL-3.0-only`, the second says what the file is (`version.rc`, the test sources and the test scripts carry the SPDX line in their own comment syntax, after the shebang or `@echo off` in the scripts, and `test\base.ini` in its comment block; the project files and the two INI files that stand for TweaksV's own, `expected_default.ini` and `layout1.ini`, carry none); a part's `.cpp` opens with a comment that explains what the part does, every switch it reads and the credit for the idea or the patterns; a part has one log tag (`kTag`, the feature name of section 4.1), one entry function `Init<Part>()` called by the feature table - a part of two modules one per module, `Init<Module>()`, which its entry calls in turn (WeaponLimits), and a part named apart from its one module that module's (Resources, `InitTextureBudget()`) - and keeps its state in file-scope variables inside an anonymous namespace; a module of a part measured first does the same with its part's tag and one entry function `Measure<Limit>()`, called by the table of the parts measured first (sections 4.3 and 11.15). Tabs for indentation; CRLF line endings in the source (git normalises them). The parts carry no code of the projects they derive from but StaticBounds, whose pattern, search and rule are adapted from the source of the Static Bounds Limit Adjuster (GPL-3.0-or-later, section 11.13); what remains of the others is the console opener in `TweaksVLog.cpp` (RageOpenV's, GPL-3.0) and the scanner's pattern parser (section 8), all three named in THIRD_PARTY_NOTICES.md.

## 3. The start-up

`DllMain` runs these steps on `DLL_PROCESS_ATTACH`, inside a `try` so that no exception leaves it, and returns `TRUE` whatever happens:

1. `IsGtaVEnhanced()`: the running program's file name is `GTA5_Enhanced.exe` (case-insensitive) or nothing more happens.
2. `CreateOrUpdateIni()`: `TweaksV.ini` exists from here on (section 5).
3. `LoadSettings()`: every setting is read once; the file is let go of afterwards (section 4.1).
4. `[TWEAKSV] ENABLED=0` stops here: the file is kept, nothing else is done. Otherwise the module pins itself (`GetModuleHandleExW` with `GET_MODULE_HANDLE_EX_FLAG_PIN`): `TweaksV.asi` stays loaded until the game exits, because the game's code calls into it once hooked, and an early `FreeLibrary` would crash the game at the next hooked call. A pin that fails is reported (`TweaksV.asi could not be pinned in memory (...): an ASI loader that unloads it later would crash the game.`).
5. `CheckForConflicts()` with `CONFLICT_CHECK=1` (section 7), before the log is started, so that the header's `Features:` line says `off` for every part the check switches off.
6. `ClearLogFile()` and `WriteLogHeader()`: the log is started and its header written (section 6.2). Lines logged before this point - the settings' problems, a pin that fails, the conflict check's lines - are kept and written after the header; the console, opened next, does not show them.
7. `OpenConsole()` with `CONSOLE=1`. A test build then runs `StartCodeDump()` (section 13.2), before anything is patched, and `StartScriptDump()`, which joins the script programs' hook when `TEST_DUMP_SCRIPT` is set (section 13.3) - before the Blips part joins it at step 8, so that its copy shows a program as the game placed it.
8. `StartFeatures()`: every part that is on, in table order (section 4.3). Each part runs its whole job here, except RageOpenV, which only hooks `GetSystemTimeAsFileTime` and does its job at the game's first time request, because the game's file system is not up in `DllMain`, and DirectStorage, which hooks `NtCreateFile` here, with `UNLOCK_FILES` `NtSetInformationFile` too - and with `DIAGNOSTIC_MODE` `DStorageGetFactory`, and `OpenFile` when the game creates its factory (section 11.8) - and Blips, which joins the script programs' hook here and does its job each time the game places `blip_controller` (section 11.9). With `DIAGNOSTIC_MODE=1` the parts measured first follow, after the parts (section 11.15).
9. `ShowStartupSummaryLater()` starts the thread that shows the start-up summary (section 6.4), unless `StartFeatures` returned true because a part shows it itself later (RageOpenV, at the first time request).
10. `DllMain` returns `TRUE`, also after an exception; one that reaches its own `try` is reported (`Unexpected exception during the start-up - the rest of TweaksV is skipped this session.`) and the summary thread started, so the box names it even when the log never started.

On `DLL_PROCESS_DETACH` the log is flushed and closed (`CloseLog`), without waiting for a lock another thread may have died holding.

The game's file version comes from the version resource of the running program (`ReadGameVersion`, four 16-bit numbers; `GameVersionNumber` packs them into one number, read once, 0 when unreadable). The PackfileLimit part chooses patterns by it; the log header prints it.

## 4. The three tables

### 4.1 Settings (`TweaksVSettings.h`)

A `SettingsSection` is a section of `TweaksV.ini` and the part it belongs to: `{ name, feature }`, the feature name being the log tag and the name in the `Features:` line and the start-up summary. The sections, in file order, which is also the order the parts start in: `kTweaksVSection` (`TWEAKSV`, `TweaksV`), `kHeapSection` (`HEAP_ADJUSTER`, `HeapAdjuster`), `kModkitSection` (`MODKIT_LIMIT`, `ModkitLimit`), `kPackfileSection` (`PACKFILE_LIMIT`, `PackfileLimit`), `kBoxStreamerSection` (`BOXSTREAMER`, `BoxStreamer`), `kDecalsSection` (`DECALS`, `Decals`), `kRageOpenVSection` (`RAGEOPENV`, `RageOpenV`), `kStoryModeSection` (`STRAIGHTTOSTORYMODE`, `StraightToStoryMode`), `kDirectStorageSection` (`DIRECTSTORAGE`, `DirectStorage`), `kBlipsSection` (`BLIPS`, `Blips`), `kWeaponLimitsSection` (`WEAPON_LIMITS`, `WeaponLimits`), `kPedPropsSection` (`PEDPROPS`, `PedProps`), `kResourcesSection` (`RESOURCES`, `Resources`), `kStaticBoundsSection` (`STATICBOUNDS`, `StaticBounds`), `kRayTracingSection` (`RAYTRACING`, `RayTracing`); `kSections` lists them in that order.

A `Setting` is `{ section, key, kind, defaultValue, minValue, maxValue, testBuildOnly, comment }` with `kind` one of `Switch` (0 or 1), `Number` (an `int` within `minValue..maxValue`) or `Text` (test builds only, never written to the file), and `comment` the short note the default file carries after the value, empty for none. The builders `Switch(section, key, on[, comment])`, `Number(section, key, value, min, max[, comment])` and `TestText(section, key)` make the entries of `kSettings`, the one table, in the order of the default file: the keys of `[TWEAKSV]` (`ENABLED`, `LOG`, `DIAGNOSTIC_MODE`, `DRY_RUN`, `CONSOLE`, `ERROR_POPUP`, `CONFLICT_CHECK`, `VERSION` with default 4 and range 2..1000000, then the test-only `TEST_BREAK_PATTERN`, `TEST_LOG_LIMIT_KB`, `TEST_DUMP_CODE`, `TEST_DUMP_SCRIPT`), then per part `ENABLED` and its own keys: `HEAP_SIZE` 2000 (1..2047), `MODKITARRAY_SIZE` 65536 (1..65536), `PACKFILEARRAY_SIZE` 13000 (1..65535), `TRAVERSAL_LIST_SIZE` 10000 (1000..100000), `DECALDEFS_SIZE` 2048 (260..16384), `MODS_FOLDER`, `OPEN_RPF`, `SKIP_RPF_CACHE_CHECK`, `SKIP_SPLASH_SCREEN`, `SKIP_LEGAL_SCREEN`, `SKIP_LANDING_PAGE`, `UNLOCK_FILES`, all on, `ACTIVE_BLIP_LIMIT` 1900 (150..1997), `WEAPON_INFO_FILES` 1024 (160..16384), `WEAPON_COMPONENTS_SIZE` 1024 (470..16384), `VIDEO_MEMORY_BUDGET` 0 (0..16384), `STATICBOUNDS_SIZE` 16000 (1..100000) and `DYNAMIC_BVH_VERTICES` 0 (0..26843545); `[PEDPROPS]` holds `ENABLED` alone. `kIniLayoutVersion` is 4 and `kIniFirstLayout` 2, the first layout with `VERSION` - its minimum - and the oldest one carried forward (section 5.3). A `static_assert` on `IniKeyCount()` pins the layout at 40 keys in the file: a new key means a new layout number. `kIniCommentColumn`, 28, is the column at which every comment of the default file starts, and a second `static_assert`, on `CommentsFitTheColumn()`, refuses a key whose `KEY=default` would reach it.

`FindSetting(section, key)` is `consteval`: it returns the table entry, and a name that is not in the table does not compile. Every part reads its settings through a named reference made that way (`kHeapSize`, `kModkitArraySize`, `kPackfileArraySize`, `kTraversalListSize`, `kDecalDefsSize`, `kModsFolder`, `kOpenRpf`, `kSkipRpfCacheCheck`, `kSkipSplashScreen`, `kSkipLegalScreen`, `kSkipLandingPage`, `kUnlockFiles`, `kActiveBlipLimit`, `kWeaponInfoFiles`, `kWeaponComponentsSize`, `kVideoMemoryBudget`, `kStaticBoundsSize`, `kDynamicBvhVertices`, `kEnabled`, `kLog`, `kDiagnosticMode`, `kDryRun`, `kConsole`, `kErrorPopup`, `kConflictCheck`, `kIniVersion`, the four test keys); the functions that work on the whole table (`IsFeatureOn`, `DescribeSettings`, `DefaultIniText`, the missing-key check of section 5.3) iterate `kSettings`.

`LoadSettings()` reads every entry once through `ReadIniValue` (a build that is not the test build skips the four test keys) and keeps the values in one array; afterwards nothing reads the file again. There is no in-game panel and no reload key, by design: the parts patch the game before it runs, so a setting changed live would change nothing. A value is parsed by its kind: a switch accepts `1`, `0`, `true`, `false`, `yes`, `no`, `on`, `off` in any case; a number is parsed with `wcstoll`, clamped to its limits with a reported problem when it lay outside, and a value that is no number is reported and the default used; a text is kept as it is. The report lines are `TweaksV.ini: [SECTION] KEY=value is not a valid on/off value - using 1.`, `... is not a number - using 2048.` and `... is outside 260..16384 - using 16384.`. A `VERSION` above 4 is reported as a file from a newer TweaksV. The readers: `IsOn(setting)`, `GetNumber(setting)`, `GetText(setting)`, `IsDryRun()`, `IsDiagnosticMode()`, and for the WeaponLimits part's guards `GuardRoom(tag, guard, partRoom, gameRoom)` - the room the part gave the game, in a test build with `TWEAKSV_TEST_GUARD_ROOM=1` the game's own (section 13.1); `IsFeatureOn(section)` is the section's `ENABLED` unless `DisableFeatureForSession(section)` switched the part off (the conflict check does that), `IsEnabledInIni(section)` the `ENABLED` alone; `DefaultIniText()` builds the default file from the table (section 5.4); `DescribeSettings()` builds the header's `Features:` line and one line per part with its values (section 6.2).

### 4.2 Patterns (`TweaksVPatterns.h`)

A `GamePattern` is `{ label, text }`: the label is the one PATTERNS.md gives the pattern (`H-E1`, `P-E-R31a`, `D-E-L12`, ...), the text its bytes in hex with one space between them and `?` for any byte. `kPatterns` lists every pattern once, in the order of PATTERNS.md, grouped per part with a comment that says what the group's matches hold. Two `consteval` checks run when TweaksV is compiled: `PatternsAreValid()` (every text is well-formed hex and wildcards, every label is unique) and `Pattern(label)`, the only way the code names a pattern, which returns the table entry and refuses to compile for a label that is not there. `PatternByte(pattern, index)` gives the byte a pattern holds at an index (-1 for a wildcard), so that a constant can be checked, when TweaksV is compiled, against the byte its pattern pins it with (`TweaksVScripts`, section 13.3). The `patterns` test suite checks that PATTERNS.md lists exactly the table's patterns with the same bytes, and that the code uses each one exactly once (section 14.2). The table holds 144 patterns. 1.0.1158.16 uses 141 of them (the packfile part chooses one of three direct-size patterns and one of two references by build), and the check boot (`DIAGNOSTIC_MODE=1` and `CONSOLE=1`, every part on, with or without `DRY_RUN=1`) looks for every one: the Blips part the script programs' `Y-E-H1`, `Y-E-N1` and `Y-E-I1` on every boot it is on (section 13.3) and its own `L-E-P1` and `L-E-P2` with `DIAGNOSTIC_MODE`; WeaponLimits its seven, `W-E-I1`, `W-E-I2` and `W-E-C1` to `W-E-C5`, on every boot it is on - `W-E-C4` through `TweaksVPools`, which StaticBounds asks too, beside its own `C-E-H1`, on every boot it is on (sections 11.10 and 11.13); PedProps eleven of its thirteen on every boot it is on, `A-E-C2` and `A-E-S1` with `DIAGNOSTIC_MODE` (section 11.11); Resources `Q-E-T1` to `Q-E-T4` while `VIDEO_MEMORY_BUDGET` is not 0, and all five, `Q-E-T5` the measurement's, with `DIAGNOSTIC_MODE` (section 11.12); RayTracing `T-E-B1`, `T-E-C1` and `T-E-C2` while `DYNAMIC_BVH_VERTICES` is not 0 or with `DIAGNOSTIC_MODE` (section 11.14); and the parts measured first their 18 with `DIAGNOSTIC_MODE` (section 11.15). A normal boot looks for fewer: `R-E-C1` only with `CONSOLE=1`, `R-E-F1..F8` only with a mods folder in the game's current directory or with `DIAGNOSTIC_MODE=1`, `Q-E-T1` to `Q-E-T4` and the three `T-E-` patterns only with their part's key not 0 or with `DIAGNOSTIC_MODE=1`, and `L-E-P1`, `L-E-P2`, `A-E-C2`, `A-E-S1`, `Q-E-T5` and the 18 of the parts measured first only with `DIAGNOSTIC_MODE=1`.

### 4.3 Features (`TweaksVFeatures.cpp`)

A `Feature` is `{ section, oldPlugins[3], peerPlugins[1], start }`: the part's section (its `ENABLED` switch and its name), up to three stand-alone `.asi` files that did its job before TweaksV and that TweaksV replaces, up to one stand-alone plugin that does its job too and stays installed because another mod needs it, and the function that starts it, which returns true if the part shows the start-up summary itself later. Such a plugin is a `PeerPlugin`, `{ file, description }` - its `.asi` file and what it is, for the start-up summary - defined once as a constant and named in the entry of every part whose job it does: `kNveLoader`, `onigiri.asi`, "NaturalVision Enhanced's loader", a mods loader that skips the splash and legal screens too and patches the sites of RageOpenV and StraightToStoryMode after TweaksV, and `kResourceExtensions`, `ResourceExtensions.asi`, "Resource Extensions [Enhanced]", a closed-source plugin for Enhanced that raises many of the game's capacities - the archive count, the story blips' threshold and extra capacity for the ray tracing of moving geometry among them - and asks to remove the heap and packfile adjusters: it stays for its other jobs, so HeapAdjuster, PackfileLimit, Blips and RayTracing are off while it is there (NOTES.md, "Conflicts"). `kFeatures` lists the parts in the order of `kSections` (checked by a `static_assert`):

`StartFeatures()` calls each start function whose part is on, each inside its own `try`: an exception ends only that part, reported as `unexpected exception - this part is skipped for this session`. `Features()` hands the table to the conflict check.

`kMeasuredFirst`, beside it, lists the parts measured first (section 11.15), one entry per limit in the order of that section's subsections: `MeasuredFirst { feature, start }`, the part's log tag and its module's `Measure<Limit>()`. It is a `std::initializer_list`, so it may be empty: a limit leaves it when its part is built - the part then gets its section and its entry of `kFeatures` - and when it is not. With `DIAGNOSTIC_MODE=1`, `StartFeatures()` starts them after the parts, each inside its own `try`: an exception ends only that measurement and is logged, not reported, since a measurement is an aid (section 12) - `DIAGNOSTIC: unexpected exception - a measurement of this part is skipped for this session.`

## 5. TweaksV.ini

### 5.1 Where it is

`GetGameFolder()` is the folder of the running program, found once from its path. `GetFallbackFolder()` is `%LOCALAPPDATA%\TweaksV`, empty when `LOCALAPPDATA` is not set. The file in use (`GetIniPathW()`): the game folder's `TweaksV.ini` if it exists, else the one in the fallback folder if that exists, else a new file - in the game folder, or in the fallback folder when the game folder cannot take it. A file in the game folder always wins; the header says when an unused copy sits in the fallback folder.

### 5.2 The own-file checks (`TweaksVFiles`)

TweaksV writes only to its own files, `TweaksV.ini`, `TweaksV.log`, `TweaksV.old.ini` and the test-build dumps, and only where each is what its path says: a plain file directly in the folder it belongs in. A link in its place could otherwise make TweaksV write to another file, which matters when the game runs as administrator. `FileFolder` says which kind of folder the file is in: `Game`, which may itself be a link (an install moved to another drive), or `Own`, TweaksV's folder in `%LOCALAPPDATA%`, which may not. `Check` refuses a file that is a reparse point, a folder, a hard link (more than one name for the same file), a file whose folder is a reparse point where that is not allowed, a file whose final path (`GetFinalPathNameByHandleW`, every link followed) is not the folder's own final path plus the name (compared case-insensitively), and a file whose attributes, folder or final path cannot be read at all. An `OwnFile` result carries the handle, the Windows error if the open failed, and `unsafe`, the reason the file is not what its path says; `ReadOnly()` tells a read-only folder (`ERROR_ACCESS_DENIED`, `ERROR_WRITE_PROTECT`) from every other failure, because a read-only game folder is normal and only logged. `FinalPathOf(path)` gives the final path of any existing file or folder the same way, empty if it cannot be read; RageOpenV compares the current directory with the game folder by it (section 11.6). `FileExists(path)` says whether a file, not a folder, is there - for the places of `TweaksV.ini`, the conflict check and DirectStorage's note on `DirectStorageFix.asi`.

- `OpenOwnFile(folder, name, where, disposition, truncate)` opens for writing with `OPEN_ALWAYS` or `CREATE_NEW`, the link itself and never its target (`FILE_FLAG_OPEN_REPARSE_POINT`), checks, deletes a file it created itself when the check fails, and empties a file that passes when asked.
- `HoldOwnFile(folder, name, where)` opens an existing file for reading without delete sharing: while the handle is open, nobody can rename, delete or replace the file or rename a folder above it, so the Win32 INI functions that open it by its path reach this very file.
- `RenameOwnFile(folder, name, newName, where)` renames through a handle on the file after the same check; a file already at the new name is replaced only when it passes the check itself, otherwise nothing is renamed.

### 5.3 Creating, updating, replacing (`TweaksVIni`)

`CreateOrUpdateIni()`:

1. An existing file (game folder first, else fallback) is held (`HoldOwnFile`); one that fails the check is reported (`TweaksV.ini (<path>) is not used: <reason>. TweaksV uses its built-in defaults this session.`) and never read.
2. A held file without the key `VERSION` under `[TWEAKSV]` has the layout of TweaksV 1.x, whatever else it holds - a 1.6.0 file, an empty or damaged one, a layout-2 file whose `VERSION` line was deleted. Only the key names of that section are read to decide; no value of such a file is ever used. The hold is released, the file renamed to `TweaksV.old.ini` through `RenameOwnFile` (an older `TweaksV.old.ini` that passes the check is replaced), the default file written in its place with `CREATE_NEW`, held, and the problem reported once: `TweaksV.ini had the layout of TweaksV 1.x. It was renamed to TweaksV.old.ini and a fresh TweaksV.ini written with the default settings - set your values again.` A file that cannot be renamed is reported in its own words every boot (`... has the layout of TweaksV 1.x and could not be renamed to TweaksV.old.ini (<reason>). Delete or rename it yourself - TweaksV uses its built-in defaults until then.`) and not read; a renamed file whose replacement cannot be written is reported once (`TweaksV.ini had the layout of TweaksV 1.x and was renamed to TweaksV.old.ini, but a fresh TweaksV.ini could not be written in <folder> (<reason>). TweaksV uses its built-in defaults this session.`), and the next boot starts without a file (step 4).
3. Any other held file gets every key of the table it is missing, written with its default through `WritePrivateProfileStringW` - without a comment: TweaksV adds none to an existing file - and logged (`TweaksV.ini: added the missing key [SECTION] KEY=value.`); a key that cannot be added is logged when the file is read-only and reported otherwise. Existing values are never changed. A file of an older layout - its `VERSION`, read as `ReadIniValue` reads a value, a number from `kIniFirstLayout`, 2, to below `kIniLayoutVersion` - is then carried forward: this layout's number is written back in the old one's place, the rest of the line - a comment after the value - as it was (the value as `GetPrivateProfileStringW` gives it, 1023 characters at most; one cut short gets the number alone), and logged, `TweaksV.ini: carried from layout 3 to layout 4 (the keys it lacked are added).`; a `VERSION` that cannot be written back is logged when the file is read-only and reported otherwise (`TweaksV.ini: VERSION=4 could not be written back (<reason>), so the file keeps VERSION=3 and is carried forward again at the next start.`). A `VERSION` that is no number, or outside that range, is left as it is for `LoadSettings` (section 4.1): no number or below 2 it is reported, above 4 it is a newer TweaksV's file.
4. No file anywhere: the default file is written in the game folder; if that fails, in the fallback folder (the folder is created) - a read-only game folder is only logged (`The game folder is read-only (...), so TweaksV.ini was created with the default settings in <folder>.`), any other reason is reported; if both fail, the built-in defaults are used and reported.

The file stays held until `ReleaseIniFile()`, which `LoadSettings()` calls once every value is read. `ReadIniValue(section, key)` reads at most 255 characters of a value through `GetPrivateProfileStringW`, cuts it at a comment - `//`, as the default file writes one, or `;` - since Windows' INI functions take everything after the `=` for the value, and trims it of spaces and tabs; nothing is read when the file is not in use. `DescribeIniLocation()` gives the header its `TweaksV.ini:` line: the path, and in parentheses whether the 1.x file was renamed and this fresh file written, whether the game folder has no file, whether this file wins over an unused copy in the fallback folder, or why the file is not used.

`DefaultIniText()` builds the file from the table: the header comment, then every section with a blank line before it and its keys in table order, each as `KEY=default` with its comment from column 28 on where it has one (`DefaultLine`), CRLF line endings. ## 6. TweaksV.log and the start-up summary

### 6.1 The log file

`WriteLog(tag, text)` appends one line, `hh:mm:ss.mmm [Tag] text`, to `TweaksV.log` and to the console when one is open. It is thread-safe (one `SRWLOCK`, held through the guard of `TweaksVLock.h`, which an exception releases too, so no failure can leave the lock taken and the next line waiting forever), lines longer than 2 KB are cut and end in `...`, and every mention of the Windows user's profile folder is written as `%USERPROFILE%` - also in its short form (`C:\Users\NAME~1`), as `%TEMP%` often has it - because logs get posted in public and that folder is usually named after the user. Lines written before the log is started (up to 1024) are kept and written after the header. The file grows to 64 MB at most; the last line then says `TweaksV.log has reached its limit of 64 MB - nothing more is written to it this session.`, and the console still gets every line.

`ClearLogFile()` starts the file each session, truncated: in the game folder through `OpenOwnFile`, else - the folder read-only, a link in the file's place, the file in use by another program - in `%LOCALAPPDATA%\TweaksV`. A read-only game folder is logged; any other reason for the fallback, and no file at all, are problems. `LOG=0` writes no file. `GetLogPathW()` is the path in use, which the message boxes print - with `LOG=0`, `(off - LOG=0)` in its place.

### 6.4 Problems and the start-up summary (`TweaksVSummary`)

`ReportFailure(tag, what)` logs `PROBLEM: <what>` under the part's tag and keeps the item (`[Tag] what`) for the start-up summary, at most 40 items, the rest counted; the list is kept under a lock held through the same guard, with the item built before the lock is taken. `ShowStartupSummary()` runs once: with nothing to show it logs nothing; otherwise, with `ERROR_POPUP=0`, it logs `Start-up summary not shown (ERROR_POPUP=0): N problem(s), see above.`, and with `ERROR_POPUP=1` it logs `Showing the start-up summary (N problem(s)).` and shows one message box, `TweaksV could not apply everything:`, with one bullet (`•`) per item, `• ... and N more.` when items were dropped, the line `The game continues without the affected parts. Details are in TweaksV.log:` with the path on the next line (`(off - LOG=0)` with `LOG=0`), and `To stop this message, set ERROR_POPUP=0 in TweaksV.ini.` `ShowStartupSummaryLater()` does that from a thread of its own, which holds a reference to the module while it runs, because a message box must not block `DllMain` or the game's thread that first asks for the time. `StartModuleThread(thread, what)` starts such a thread - this one, the one for problems after the summary (below), RageOpenV's start-up check and its check for packs made for GTA V Legacy (`Legacy packs check`, section 11.6), DirectStorage's checks and its `OpenFile` summary, the static bounds check (`static bounds check`, section 11.13), and the measurements' threads (section 6.6) and RayTracing's sampling thread (`ray tracing buffer sampling`, section 11.14), which never end and keep it - with the extra reference to the module, which the thread drops when it ends; one that cannot start is logged, `The <what> thread could not be started (Windows error N).`; when that is the start-up summary's own thread, every problem of the session stays in the log alone (NOTES.md, T-SUMMARY). Both threads of this module run inside a `try`: a box that cannot be built is logged (`Unexpected exception while showing the start-up summary - the box is not shown; the problems are logged above.`) and skipped, and the next late problem starts a new thread.

A problem reported after the summary was shown - a part that stops working later, such as a file in the mods folder that RageOpenV cannot open, but also a finding that is no part failing, such as the packs made for GTA V Legacy that RageOpenV's check names or a file a guard of WeaponLimits refuses, and the static bounds' check (NOTES.md, T-LATEBOX) - is shown by a thread of its own a second later, with the heading `TweaksV: a part stopped working after the start-up:`, at most three such boxes per session, a list of more than 40 ending in `• ... and N more.`; after that, and with `ERROR_POPUP=0`, such problems are only logged. Test builds show no box while the environment variable `TWEAKSV_TEST_NO_BOXES` is `1` and log `TEST BUILD: message box not shown (TWEAKSV_TEST_NO_BOXES=1): <heading>` instead, so the test suites never wait on one.

### 6.5 The console

`CONSOLE=1` opens a console window (`AllocConsole`) once the header is written, and it mirrors every log line from `Console opened (CONSOLE=1).` on; the RageOpenV part then NOPs the game's call that would hide it (section 11.6). The console is a testing aid: when it cannot be opened or kept, the log says so and nothing is reported.

### 6.6 The measurements (`TweaksVMeasure`)

`DIAGNOSTIC_MODE`'s ten measurements of the parts - the box streamer's searches, the decal definitions registered, RageOpenV's file requests and archive headers, DirectStorage's opens in the game folder, the blip pool's slots in use, the `weapons.meta` files and the weapon component definitions loaded (WeaponLimits), the props per anchor of the ped models (PedProps), the streamed textures and buffers against their budget (Resources) and the ray tracing buffer's use (RayTracing) - the two of the parts measured first (section 11.15), DirectStorage's `UNLOCK_FILES` summary and the weapon infos guard's report (section 11.10.1) share one loop. A part describes its measurement as a `Measurement { thread, firstMs, numbers, summary, start }` - the thread's name, when the first summary comes, a function whose number changes whenever the summary has something new to say, the function that writes the summary, given that number, and, if given, an event the part sets at the first thing it counts, which the thread waits for before `firstMs` begin, so that a hook never starts a thread itself (the `UNLOCK_FILES` summary, 10 seconds after the first open counted; an event that could not be made starts the clock at once) - and starts it with `StartMeasurement`, which starts its thread through `StartModuleThread` (section 6.4); the thread never ends, so it keeps its reference to the module. The thread writes the first summary `firstMs` in - `kFirstSummaryMs`, 10 seconds, or `kSummaryEveryMs`, a minute, for DirectStorage's open summary - always, and then one every minute while the number changes - in a test build every `TWEAKSV_TEST_SUMMARY_MS` milliseconds when that is set (section 13.1) - inside a `try`, so nothing leaves the thread. A measurement whose thread cannot start is logged (`The box streamer summary thread could not be started (Windows error 8).`, the names being `box streamer summary`, `decal definitions summary`, `RageOpenV summary`, `DirectStorage open summary`, `UNLOCK_FILES summary`, `blip pool summary`, `weapon infos summary`, `weapon components summary`, `ped props summary`, `texture budget summary` and `ray tracing buffer summary`, and for the parts measured first `siren settings summary` and `siren count summary`), not reported: it is an aid that changes nothing in the game (section 12) - but for the weapon infos guard's report, `weapon infos guard report`, which is the guard's own: its thread not started, the guard is not set up, a problem of the part (section 11.10.1). RayTracing's measurement samples its buffer every 50 ms on a thread of its own beside the loop, `ray tracing buffer sampling` (section 11.14). `kMaxLinesPerKind`, 20,000, is the cap of every kind of line that comes per event (section 12).

## 7. The conflict check (`TweaksVConflicts`)

`CheckForConflicts()` looks in the game folder and its `scripts` and `plugins` subfolders - the three places an ASI loader loads from, `kLoaderFolders` in `TweaksVConflicts.h`, which DirectStorage's look for `DirectStorageFix.asi` uses too - for every old plugin and every plugin that stays of every feature (section 4.3). An old plugin found switches its part off for the session (`DisableFeatureForSession`) and is reported: `Old plugin found: <path>. TweaksV's <Feature> part is switched off for this session so nothing is patched twice. Delete the old file - TweaksV replaces it.` `DecalPatch.asi` is the old plugin of two parts and switches both off; `StaticBoundLimitAdjuster.asi` and `StaticBoundsLimitAdjuster.asi`, the two names of one original, are both old plugins of StaticBounds. A plugin that stays does the same while its part is on in `TweaksV.ini` - `IsEnabledInIni`, not `IsFeatureOn`, so that an old plugin found before it, which switched the part off already, does not keep it from being said - and is reported in words of its own, with the switch that stops the message: `<path> is installed and does this job too (<description>): TweaksV's <Feature> part is switched off while it is there, so nothing is patched twice. To stop this message, set ENABLED=0 under [<SECTION>] in TweaksV.ini.` `onigiri.asi` is the plugin that stays of two parts and reports both, `RageOpenV` under `[RAGEOPENV]` and `StraightToStoryMode` under `[STRAIGHTTOSTORYMODE]`, and `ResourceExtensions.asi` the plugin that stays of four, `HeapAdjuster`, `PackfileLimit`, `Blips` and `RayTracing`; a part already off in `TweaksV.ini` gets no item, only a line in the log, not a problem: `Conflict check: <path> is installed; TweaksV's <Feature> part is off in TweaksV.ini already.` Every find is kept per part, whatever `TweaksV.ini` says of it, and `IsPluginInstalledFor(section)` answers from it - no file is looked for again: false when the check found none or did not run (`CONFLICT_CHECK=0`) - for a part that leaves the game's code to such a plugin even while `TweaksV.ini` switches that part off: StaticBounds, which makes no hook on the script programs while a plugin that does Blips' job is installed (section 11.13). With no file of either kind found the log says `Conflict check: none of the plugins that do the job of one of TweaksV's parts were found.`; when a plugin that stays is found next to parts that are all off, its lines are written instead, so the log always shows what the check found. `IsInsideGameImage(p)` is the shared test for an address inside `GTA5_Enhanced.exe`'s image, from its PE headers read once.

## 8. The scanner (`TweaksVScanner`)

The scanner finds TweaksV's patterns in the running game's code. `GTA5_Enhanced.exe` is encrypted on disk, so the code is only readable in memory, and a game update changes it: what the scanner finds is the one thing that must be maintained after an update (PATTERNS.md, "When Game Updates").

- The image is read once: `GTA5_Enhanced.exe`'s base and size from the module information, its executable sections from the PE headers (read only where they lie inside the image; with no executable section the whole image is searched).
- Every search reads the readable parts of those sections afresh (`ReadableCode`: `VirtualQuery` over each section, committed and readable pages only, neighbouring regions joined), because TweaksV itself changes protections between two searches and a page the game protects must be skipped, not crash the game.
- A pattern's text is parsed into bytes and a mask (`ParsePattern`: tokens of exactly two hex digits, or `?`; any other token, or a text of wildcards only, refuses the pattern - nothing in the parser can throw - logged as `Pattern <label> is not valid (treated as not found): <text>`), and compiled with the positions of its two rarest fixed bytes, rarest by how often each byte occurs in the first 256 KB of the game's code (`ByteCounts`, read once). This only changes how fast the search is, never what it finds.
- `FindIn` compares those two bytes at 16 positions at a time with SSE2 and checks the whole pattern only where both match; a match must lie wholly inside one readable range.
- `Scanner::Find(pattern)` returns the one match or `nullptr`: it asks `FindAll(pattern, 2)`, and a pattern that matches twice is not used, because what would be written over cannot be known - logged as `Pattern <label> matches 2 or more times - not used (the site must be unique).`, and the part gives its `<label> was not found.` as for a miss (the heap, the three screens, RageOpenV's patterns); `Scanner::FindAll(pattern, limit)` returns every match in address order up to `limit` (a site the game must have exactly n times is asked for n + 1, so that an n + 1th match shows); both log a miss as `Pattern <label> not found: <bytes>` and, with `DIAGNOSTIC_MODE`, the line of section 6.3 with the RVA, the number of matches (exact up to 99, `100+` from 100 on) and the bytes of the match, 32 at most, plus one line for each of the first ten matches with 16 bytes before and 48 from its start, for a pattern that matches more than once, so that a longer pattern can be chosen that matches only the place it is meant for. The scanner's tag is `[Scanner]`.
- `Scanner::FindRipRelativeLeas(target, limit)` finds every `lea r64, [rip+disp32]` (a REX prefix with the W bit, opcode `8D`, ModRM mod 00 r/m 101: 7 bytes) in the readable code whose displacement leads to `target`, in address order up to `limit`, with the same 16-at-a-time comparison on the opcode and ModRM bytes. It is how the relocation core finds the loads of an array the game loads in places no pattern can tell apart. `Scanner::FindRipRelativeReferences(target, limit)` is the same search for every `lea r64, [rip+disp32]` and every `mov [rip+disp32], r64` (the same prefix and ModRM, opcode `8D` or `89`), one helper behind both: how the core checks that the references an array's patterns name are all the game has. Nothing is logged.
- `Scanner::FindCallsTo(target, limit)` finds every `call rel32` (`E8` and a rel32: 5 bytes) in the readable code that leads to `target`, in address order up to `limit`, with the same 16-at-a-time comparison on two bytes: the opcode, and the rel32's lowest byte, which a call at p must hold as the lowest byte of target - (p + 5), so that over 16 positions in a row those bytes count down by one; the whole rel32 is compared only where both match. It is how the PedProps part checks that the game calls a function exactly as often as the research found (section 11.11). Nothing is logged.
- `Scanner::FindRipRelativeStores(target, size, limit)` finds every instruction in the readable code that writes to memory at `[rip+disp32]` and so to any of the `size` bytes from `target`, in address order up to `limit`, each given by its first byte, its prefixes counted: a `mov` of 1 to 8 bytes from a register or an immediate, the read-modify-writes of the integer unit (`add`, `or`, `adc`, `sbb`, `and`, `sub`, `xor`, `inc`, `dec`, `not`, `neg`, the shifts and rotations, `xchg`, `xadd`, `cmpxchg`, `cmpxchg8b` and `16b`, `setcc`, `bts`, `btr`, `btc`, `shld`, `shrd`, `pop`) and the SSE and AVX moves and extracts of 1 to 32 bytes (`movss` to `movdqu`, `movnti`, `movbe`, `pextr*`, `extractps`, their VEX forms, `vextract*128`, `vcvtps2ph`, the masked moves); x87 stores and AVX-512's are not looked for. Every ModRM of mod 00 and r/m 101 is found 16 positions at a time with SSE2, as the other searches find their bytes, and its disp32 checked to lead near the range - within the 4 bytes of an immediate and the 32 of the widest store before it - before the bytes in front of it are read as an instruction, the way the processor reads one that starts there: a VEX prefix first, then the escapes `0F 38`, `0F 3A` and `0F`, then a one-byte opcode, a REX right before the opcode and up to four legacy prefixes before that. The immediate after the disp32 counts, since the rip a store's operand is counted from lies past it; a prefix that narrows a store (`66`, `F2`, `F3`) is not counted for its width, since it may belong to the instruction before, so a store is taken for at most as wide as it can be, never narrower. It is how the texture budget checks that the start-up's two stores are the budgets' only writers (section 11.12). Nothing is logged.
- Test builds: `TEST_BREAK_PATTERN=<label>` makes that pattern count as not found (`TEST BUILD: pattern <label> is treated as not found (TEST_BREAK_PATTERN).`), to watch its part be skipped cleanly.

The pattern parser is an altered version of ScriptHookVDotNet's memory scanner (THIRD_PARTY_NOTICES.md); the search is TweaksV's own.

## 9. The patch module (`TweaksVPatch`)

Every change to the game's code goes through this module, so that every part writes the same way and no part has to know about page protection, `DRY_RUN` or `DIAGNOSTIC_MODE`.

- **`WriteCode(writes, tag)`**: `writes` is a list of `CodeWrite { address, bytes, what }`. A write without address or bytes stops everything. With `DRY_RUN` nothing is written and each write is logged as `DRY_RUN: would patch the <what>: <old> -> <new>`. Otherwise every page any write touches is made writable first (`PAGE_EXECUTE_READWRITE` for a page that was executable, `PAGE_READWRITE` otherwise; a page that is already writable is left; a page that is not committed memory, a guard page, or one `VirtualProtect` refuses stops everything before a byte is written, with the protections changed so far put back, and the reason logged), then all bytes are written, then every page gets its own protection back, newest first - through a guard that runs on every exit, an exception included; nothing that can throw runs while a page is writable, so the old bytes for the log are read before and the lines written after - and `FlushInstructionCache` makes the processor see the new code; with `DIAGNOSTIC_MODE` each write is logged as `DIAGNOSTIC: <what> at <address>: <old> -> <new>`. False means nothing was written. `BytesOf(value)` gives the bytes of a value for a write.
- **`RedirectCalls(redirects, alsoWrite, tag)`**: `redirects` is a list of `CallRedirect { site, function, what, original }`, each a 5-byte relative call (`E8 rel32`) in the game to send to `function`; `original`, when given, receives the function the call led to, and is set before the call is rewritten, so a hook that calls it is ready the moment it can run. A site that is not a call stops everything. With `DRY_RUN` each is logged as `DRY_RUN: would redirect the <what> at RVA ...` and only `WriteCode(alsoWrite)` runs, which writes nothing either. Otherwise: a block of 16 bytes per call is allocated near the game (`AllocateNearGame`, read/write), each stub written as `FF 25 00 00 00 00` followed by the 8-byte address of `function` and two `CC`, the block made read+execute and never changed again (a call stub is never writable and executable at once), and then, in one `WriteCode`, every call's rel32 pointed at its stub together with `alsoWrite`. A call reaches only 2 GB, which is why the stubs sit near the game; a stub out of reach, no memory near the game, or a block that cannot be made read+execute stops everything with nothing changed.
- **`HookFunctions(hooks, tag)`** hooks functions at their start with MinHook: `FunctionHook { function, hook, original, what }`; every hook is created and queued, then all are switched on together (`MH_ApplyQueued`: the threads are frozen once per group, not once per hook); if any step fails, the hooks made so far are removed again and the reason logged: `<what> could not be hooked (MinHook: <status>)` when a hook cannot be created or queued, `The N hooks could not be switched on (MinHook: <status>)` when they cannot be applied, with ` - none of the N hooks is on.` for a group of more than one. `original` receives MinHook's trampoline. **`HookExport(module, function, hook, original, target, tag)`** hooks an exported function of a loaded DLL at once (`GetSystemTimeAsFileTime`, DirectStorage's exports, `NtCreateFile`, `NtSetInformationFile`) and hands back its address in `target`; **`DisableHook(function, tag)`** switches a hook off again, the function's own bytes back and the trampoline kept for a thread that is inside the hook right now. MinHook is initialised on first use; its trampolines are writable and executable, an accepted open issue (NOTES.md, T-HARDEN).
- **`AllocateNearGame(size)`**: `size` bytes, read/write, committed and zeroed, within 1 GB below the game's image, where a rel32 in the game's code reaches: the free regions below the image are walked by allocation granularity, as MinHook's own allocator does, and the first that gives `size` bytes is taken. For the moved arrays and the call stubs.
- The readers: `CallTarget(site)` (the target of an `E8 rel32`, or `nullptr`), `Rel32Target(address)` (where a rel32 or a rip-relative disp32 at that address leads), `StartsWithJump(address)` (`E9`, `EB` or `FF 25`: the usual sign of another mod's hook), `IsFunctionStart(address, detail)` (the game's unwind data, asked of Windows with `RtlLookupFunctionEntry`, says so - `a function start (unwind data)`; an address inside a function gives `inside the function at RVA ... (unwind data)`; for code without unwind data the byte before it, read only where it is readable (`no unwind data, the byte before it cannot be read`), must be `CC`, `90` or `C3` - `no unwind data, byte before it CC`), `IsReadable(address, size)` (committed, readable, no guard page, over the whole range; used before any byte outside a pattern's match is read), `CopyMemorySafely(target, source, size)` (a copy that catches an access violation and returns false - nothing else is caught - for memory that may change or be freed between a check and the read: the pointers the game's DirectStorage calls hand the DirectStorage part's hooks, the game's heap data a measurement or a guard walks while the game changes it, sections 11.10 to 11.15), `DescribeAddress`, `HexBytes`.

## 10. The relocation core (`TweaksVRelocation`)

Five parts move one of the game's static arrays to a larger one and raise the limit the game's code carries for it: the modkit array, the packfile array, the box streamer's traversal list, the decal definitions array and the weapon component list, whose size no instruction carries - it is the distance to the count that follows the list. They describe their array in tables; the core does the work once for all of them.

### 10.1 The tables

- `ReferenceSite { offset, opcode, opcodeSize }`: where a match holds the rel32 of a `lea r64, [rip+disp32]` or of a rip-relative `mov` that addresses the array, so that the array is the address after the rel32 plus its value; `opcode` are bytes the instruction must start with, right before the rel32, or none.
- `LimitSite { kind, offset, opcode, opcodeSize, valueOffset, mul, add, end }`: `Immediate`, an imm32 at `valueOffset` that holds `N x mul + add` with N the array's size; `Variable`, the rel32 at `valueOffset` of a variable the game compares against, which holds `N + add`; or `Follower`, for an array whose size no instruction carries, the disp32 at `valueOffset` of an instruction that ends at `end` - an immediate may follow the disp32 - and addresses a variable lying right after the array: the distance from the array to it is N, in entries, and the variable is left as it is, never written (the weapon component list's count); `offset` is the instruction, `opcode` its first bytes, or none.
- `Anchor { pattern, matches, hasReference, reference, limitCount, limits[3] }`: a pattern of the part, how often it must match (1, or more for a site the game repeats), and what every match holds: a reference, up to three limits, both, or neither - a site the part reads itself through the plan. The builders: `Rel32(offset, opcode, opcodeSize)`, `Imm32(imm32, mul, add)`, `Imm32(instruction, opcode, opcodeSize, imm32, mul, add)`, `Variable(rel32, add)`, `Follower(instruction, opcode, opcodeSize, disp32, end)`, `Site(pattern)`, `Reference(pattern, site)`, `Limit(pattern, site)`, `Limits(pattern, matches, a, b[, c])`, `Repeated(pattern, matches, limit)`, `ReferenceAndLimit(pattern, ref, limit)`.
- `RelocationSpec { tag, name, sizeName, job, entrySize, maxEntries, setting, anchors, scannedReferences, leaPrefixes, leaPrefixCount, expectedReferences }`: the part's log tag, the array's name for the log (`modkit array`, `box streamer's traversal list`), the name of its size (`modkit list size`), the start of every failure line (`The modkit limit is not changed`), the bytes per entry, the new array's size (always allocated in full, and the setting's maximum), the setting that asks for the size, the anchors, for an array whose loads no pattern can tell apart exactly how many `lea` must load it, found by its address, with the REX bytes they may start with (`48` or `4C` for the decals and the weapon component list; any with REX.W for the box streamer), and for an array moved by its anchors' references how many references the game's code has to it (`expectedReferences`: 6 for the modkit array, 33 for the packfile array; 0, not checked, for the other three).
- `RelocationPlan { array, gameSize, size, matches, references, limits }`: what was found: the game's own array, its size, the size to use, every anchor's matches (for the sites a part reads itself), the rel32 fields that are moved, the limits as `FoundLimit { value, mul, add }`.

### 10.2 `FindRelocation(spec, plan)`

Everything is found and checked before anything is written, and the first failure reports `<job> this session: <why>` and leaves the game as it is. A spec whose tables name no reference, or no limit, is refused as the part's own mistake. The anchors are worked through in table order - each one's matches, then for each match its reference and its limits - so a missing pattern late in the table is reported only after the sites before it passed:

1. The anchor must match exactly as often as it says (`FindAll` asks for one more): `<label> was not found.` or `the game code holds <label> N [or more] times, not the expected M.` (` or more` when more were found than expected).
2. Its reference: the instruction is readable and starts with the opcode when one is given (`is not the expected instruction (<bytes>)`); its target is logged with `DIAGNOSTIC_MODE` (`DIAGNOSTIC: reference at RVA ... -> RVA ... (<label>)`); the first reference's target must lie inside the game (`the <array> is not inside the game: <address> (another mod may have moved it already).`), every other must point at the same address (`the references to the <array> do not all point to the game's own array: <a> and <b> (<label>).`).
3. Its limits: readable, the expected instruction; a variable must lie inside the game; its value decodes to N through its encoding (`holds V, which is <encoding> for no size` when it does not divide), logged as `DIAGNOSTIC: limit[ variable] at RVA ... holds V (<encoding>, <label>) -> game size N`; a follower's variable must lie inside the game (`the variable that follows the <array> is not inside the game: <address> (<label>).`) and a whole number of entries after the array (`the variable at RVA ... does not lie a whole number of E-byte entries after the <array> at RVA ... (<label>).`), the distance N entries, logged as `DIAGNOSTIC: limit variable at RVA ... lies D bytes after the <array> (<label>) -> game size N`, and a table that names a follower before a reference to the array is the part's own mistake (`its tables name the variable that follows the <array> before a reference to it.`); the first size decoded in the whole job must be plausible (`the game's own <sizeName>, N, is not plausible.` beyond `maxEntries` or zero), every other must agree (`the limits of the <array> disagree about the game's own size: A and B (<label>).`).

Then:

4. The array is logged: `DIAGNOSTIC: the <array> is at RVA ... - N entries of E bytes`.
5. The references that are moved: the anchors' references, or - with `scannedReferences` - every `lea` that loads the array (`FindRipRelativeLeas`, each logged as `DIAGNOSTIC: reference at RVA ... -> RVA ... (lea scan)`), which must be exactly that many (`the game code loads the <array> in N [or more] places, not the expected M (another mod may have moved some of them, or the game has changed).`) and each start with an allowed prefix (`the load of the <array> at RVA ... is not a "lea r64, [rip+disp32]" with a 48 or 4C prefix: <7 bytes>.`).
6. With `expectedReferences`, the anchors' references must be every one the game has, because one no pattern names would keep the game's own, smaller array while the limits are raised: `FindRipRelativeReferences` (each site logged with `DIAGNOSTIC_MODE` as `DIAGNOSTIC: reference at RVA ... -> RVA ... (scan)`, the RVA of its rel32, as the anchors' lines have it) must find exactly that many (`the game code holds N [or more] references to the <array>, not the expected M (another mod may have moved some of them, or the game has changed).`), and every one must be an anchor's rel32 (`the reference to the <array> at RVA ... is not one its patterns name (another mod may have moved some of them, or the game has changed).`).
7. The size to use: the setting, clamped to the game's own size..`maxEntries`, reported when it lay outside (`TweaksV.ini: <KEY>=x is outside A..B - using C.`, `ReportFailure`), so that the start-up summary names the size really used - the settings' own report (section 4.1) names only the table's limits. Smaller than the game's own would shrink the array.

### 10.3 `ApplyRelocation(spec, plan, alsoWrite, redirects, also)`

With `DRY_RUN`: `DRY_RUN: would move the <array> (N references) and raise its limit from A to B (M sites)<also>.` - ` (M sites)` only where a limit is written - and nothing else. Otherwise the game's own entries must be readable (`the game's own <array> cannot be read.`), the new array is allocated in full (`entrySize x maxEntries`, `AllocateNearGame`; `the new <array> could not be allocated near the game.` when that fails) and the game's own entries are copied into it, the rest staying zero - so an array the image initialises keeps its content - every reference's rel32 is recomputed for it with the int32 distance check (`the new <array> is out of reach of the game code at RVA ...`), every limit is re-encoded for the new size (`N x mul + add`) - a follower stays as it is - the part's own writes are added, and all of it is written in one `WriteCode` - or, when the part redirects calls too, one `RedirectCalls` - all or nothing (`the game code could not be changed (details in TweaksV.log).` when not). Then `The <array> moved and its limit raised from A to B entries.` The write lines carry `<array> reference` and `<array> limit` as their `what`.

What does not fit the core stays in the part's file and uses the plan: the packfile's hooked call, the box streamer's counted calls, the decals' count, loop and measurement, the weapon components' count, pool size call and measurement (section 11).

## 11. The parts

Each part reads its switches once, at its start-up (RageOpenV's runs inside its one-shot time hook); the hooks that run per call never read them. The game facts - the patterns, what each match holds, the offsets - are PATTERNS.md's; NOTES.md lists each part's behaviour and measurements. Here is the mechanism.

### 11.1 HeapAdjuster (`InitHeapAdjuster`)

The game sizes its memory heap with one immediate in its start-up code: the imm32 of a `mov edx, imm32` that `H-E1` matches, the size in bytes at +1. `HEAP_SIZE` in MB, 1..2047 - the most whole MB that imm32 holds as a positive int32. Steps: the match must start with `BA`; the value must be a whole number of MB other than 0 (`the game code found holds an unexpected value (0x...)`), logged with `DIAGNOSTIC_MODE` as `DIAGNOSTIC: heap size at RVA ... holds 646 MB`; a value of 1024 MB or more - up to 4095 MB, since the `mov` zero-extends its imm32, past what `HEAP_SIZE` allows too - is not the game's own (646 MB on the current build): another heap adjuster set it, and the part leaves it, logs `The heap size is not changed this session: another heap adjuster already set it to N MB - left as it is.` and reports nothing; the size to use is the setting clamped to the size found..2047, reported when it lay outside (`TweaksV.ini: HEAP_SIZE=100 is outside 646..2047 - using 646.`), so that the start-up summary names the size really used; a heap that already has the size asked for is logged and left (`Heap size is 646 MB already (HEAP_SIZE=100) - nothing to patch.`); otherwise one `WriteCode` of the new imm32, computed in 64-bit arithmetic, `what` = `heap size (A MB -> B MB)`, then `Heap size patched: A MB -> B MB.` Failures: `The heap size is not changed this session: H-E1 was not found.`, `... the game code found is not the expected instruction (<bytes>).`, `... the game code could not be made writable (details in TweaksV.log).`

### 11.2 ModkitLimit (`InitModkitLimit`)

The game's array of vehicle modkit IDs: 1024 entries of 2 bytes on the current build, loaded by six `lea` (`M-E-R1..R6`, the rel32 at the offset PATTERNS.md gives) and sized by eight immediates (`M-E-L1..L8`: N-1, N+3, N+3, N+3, N+3, 2N, N-1, N-1; `M-E-L2`'s, which lies past its pattern, checked as the imm32 of `cmp rdi, imm32`, `48 81 FF`). Entirely on the core: spec `{ "ModkitLimit", "modkit array", "modkit list size", "The modkit limit is not changed", 2 bytes, 65536 entries, MODKITARRAY_SIZE, the 14 anchors, no scanned references, 6 expected references }` - the six leas must be every reference the game's code has to the array; `FindRelocation`, then `ApplyRelocation` with nothing of its own. Modkit IDs are 16-bit, which caps the array at 65536.

### 11.3 PackfileLimit (`InitPackfileLimit`)

The game's array of RPF archives: 7260 entries of 8 bytes on the current build, referenced by 33 instructions - the 32 of `P-E-R01..R30`, `P-E-R32` and `P-E-R33` on every build, plus `P-E-R31a` on builds from 1.0.1158.13 or `P-E-R31b` before; the references of `P-E-R09` and `P-E-R17`, which lie past their patterns, checked as `lea rcx` (`48 8D 0D`), `P-E-R32`'s as `lea r15`, `P-E-R33`'s as `lea rcx` - and sized by two limits: an immediate, `P-E-D3` from 1.0.1158.13, `P-E-D2` from 1.0.1013.17, `P-E-D1` before, each a `cmp rcx, imm32`, and a variable the game compares an archive index against (`P-E-I1`, the rel32 of a `cmp eax, [rip+disp32]`), which holds four less than the array's size - the core's `Variable(2, -4)` keeps that margin: the variable must hold N-4 and gets the new size minus four. The anchors are assembled at start-up by the game's file version (`GameVersionNumber`; without one: `The packfile limit is not changed this session: the game's file version could not be read, so the patterns for this game build cannot be chosen.`), the call site `P-E-H1` last as a `Site`. After `FindRelocation` the part reads that site: the call at +0x10 of the match must be readable and lead into the game (`the call that reads the game's streaming configuration at RVA ... is not a call into the game (another mod may have hooked it already).`), logged with `DIAGNOSTIC_MODE` as `DIAGNOSTIC: streaming configuration call at RVA ... -> RVA ...`. `ApplyRelocation` then takes that call as a redirect, in the same all-or-nothing write as the 33 references and 2 limits, to `SetStreamingInterface(char* configuration)`: it replaces the archive count at offset 24 of the configuration the game read from `gameconfig.xml` with the new size - exactly, also a count above it: the game's own configuration holds 8512 on 1.0.1158.16, more than its array's 7260, so a `PACKFILEARRAY_SIZE` below 8512 lowers the count - logs `The archive count of the game's configuration, 8512, is replaced by 13000.` (nothing may throw there: the log line is in a `try`), and calls the game's own function. The status lines: the core's, and `The streaming configuration call at RVA ... is redirected: the archive count the game's configuration holds is replaced by N when the game reads it.` Archive indices are 16-bit, which caps the array at 65535. Spec: `{ "PackfileLimit", "packfile array", "packfile list size", "The packfile limit is not changed", 8 bytes, 65535 entries, PACKFILEARRAY_SIZE, the anchors of the build, no scanned references, 33 expected references }` - the 33 must be every reference the game's code has to the array (25 `lea` and 8 `mov` stores on 1.0.1158.16), which the dry-run line names (`DRY_RUN: would move the packfile array (33 references) and raise its limit from A to B (2 sites) and redirect the streaming configuration call at RVA ...`).

### 11.4 BoxStreamer (`InitBoxStreamer`)

The game's box streamer answers "which map boxes lie in this area" in four query functions that hand one static list of 1000 entries of 8 bytes, and its capacity, 1000, as the fifth argument (`mov dword ptr [rsp+20h], imm32`) to one of two tree searches; a search stops 16 entries short of the capacity (`kSearchHeadroom`, a game fact in PATTERNS.md, which is also the measurement's threshold). Eight `lea r64, [rip+disp32]` load the list, two per query function; two of the functions are near-identical copies, so the second `lea` of each cannot be told apart by the bytes around it. The anchors: `B-E-L1` a limit (the capacity's imm32, N), `B-E-L2..L4` a limit and a reference (the `lea r13, [rip+disp32]` that follows), and `scannedReferences` = 8 with any REX.W prefix: the core takes the list's address from the three `lea`, scans the code for every load of it, which must find exactly eight, and moves all eight. The part's own, with `DIAGNOSTIC_MODE` only: the call to the tree search after each capacity site (offsets 30, 34, 42, 30 in the four matches; the first and third call one search, the second and fourth the other) must be readable and lead into the game (`the tree-search call at RVA ... is not a call into the game (another mod may have hooked it already) (B-E-L2).`), and each pair to the same function (`the tree-search calls of the box streamer do not lead to the same function: ... (B-E-L3).`), logged as `DIAGNOSTIC: tree-search call at RVA ... -> RVA ...` - a call that fails either check refuses the whole job, the list included: the one place where `DIAGNOSTIC_MODE` changes what a part does (section 12), because the measurement is the reason the switch is on; the four calls are then redirected in the same write as the references and capacities (`... and redirect the 4 tree-search calls (DIAGNOSTIC_MODE)` in the dry-run line) to two counting wrappers, `CountedSearch0` and `CountedSearch1`, which call the game's search with the game's arguments and count the result with atomics - nothing else on the game's streaming thread - and the measurement (section 6.6; its thread, if it cannot start, is logged as `The box streamer summary thread could not be started (...).`) logs, announced by `DIAGNOSTIC: the 4 tree-search calls are counted; a summary follows after 10 seconds, then every minute while the numbers change.`, 10 seconds in and then every minute while the number of searches changes, `DIAGNOSTIC: N searches so far; the largest returned X of 10000 entries; Y returned more than the game's own list (1000 entries) could hold.` - ending `could hold (the list has the game's own size, so no search can exceed it).` when `TRAVERSAL_LIST_SIZE` keeps the game's own size, because a search then stops where the game's own would and Y is 0 by construction. ### 11.5 Decals (`InitDecals`)

### 11.8 DirectStorage (`InitDirectStorage`)

With DirectStorage, the game asks it to open every file in the game folder at start-up, subfolders included (`IDStorageFactory::OpenFile`), and DirectStorage opens each with `CreateFileW` for reading while letting others only read it (`NtCreateFile` with access 0x80100080, share `R--`, options 0x48) and keeps it open, so mods cannot write their own files there and scripts cannot be reloaded while the game runs. The part uses no game pattern, and its job needs no DirectStorage: it hooks `NtCreateFile` in `ntdll.dll` and decides every open by its own name, access and sharing, and with `UNLOCK_FILES` `NtSetInformationFile` as well, deciding every rename that replaces a file by its target, whoever makes them. With `UNLOCK_FILES=0` and `DIAGNOSTIC_MODE=0` it does nothing (`UNLOCK_FILES=0 and DIAGNOSTIC_MODE=0 - nothing to do.`). It logs the versions of `dstorage.dll` and `dstoragecore.dll` in the game folder and whether `dstorage.dll` is loaded (`dstorage.dll <version>, dstoragecore.dll <version>; dstorage.dll is loaded.`, a version being four numbers, `not found` or `unknown version`), as information. With `CONFLICT_CHECK=0`, an installed `DirectStorageFix.asi` is noted (`Note: <path> is installed as well - it changes DirectStorage's file opens, too.`). With `DRY_RUN` one "would" line per hook of a job that is on and nothing else: `DRY_RUN: would hook NtCreateFile so that the game folder's other files are opened with write and delete sharing (UNLOCK_FILES).` and `DRY_RUN: would hook NtSetInformationFile so that a rename inside the game that replaces a file in the game folder gets POSIX semantics (UNLOCK_FILES).`, and with `DIAGNOSTIC_MODE` `DRY_RUN: would hook dstorage.dll to log the game's DirectStorage calls.` and `DRY_RUN: would hook NtCreateFile to log the opens in the game folder.`

- `NtCreateFile` is hooked at the start-up (`HookExport`) whenever `UNLOCK_FILES` or `DIAGNOSTIC_MODE` is on, one hook for both jobs, `dstorage.dll` loaded or not: `UNLOCK_FILES: NtCreateFile is hooked - a read-only open of a file in the game folder other than .rpf and .cache that shares reading gets write and delete sharing too, so those files stay free for other programs.` A hook that cannot be made is a problem of the start-up summary with `UNLOCK_FILES` (`The files in the game folder are not unlocked this session: NtCreateFile could not be hooked (details in TweaksV.log).`), and `HookExport`'s line alone with `DIAGNOSTIC_MODE` alone.
- With `UNLOCK_FILES`, `CheckOpen` decides before the call, on the stack - no memory allocation, no lock of TweaksV's, nothing that can throw - every field of the call read within the length it gives, under a guard that catches a bad pointer; an open made on a thread that is inside one of TweaksV's hooks (`t_inside`) is not examined. Where the open lies: a name `\??\C:\...` (`\??\UNC\server\share\...` for a game folder on a network share) is compared with the game folder, letters in ASCII case - below it, the game folder itself, or outside, a sibling folder whose name starts with the game folder's and every other spelling (a device, `\Device\...`) among the outside; a name relative to a folder handle, which is what Windows makes of every relative path that lies in the current directory, lies below the game folder when that handle is the game folder's, told by its identity - `FileIdInformation`'s volume serial number and 128-bit file ID, on a file system without them `FileInternalInformation`'s 64-bit file number with `FileFsVolumeInformation`'s serial number, queries that need no access to the handle (the current directory's is opened for traversing only, which `GetFileInformationByHandle` is refused) and leave the caller's last error alone; the game folder's is read once before the hook is made, the handle's asked of Windows once per such open, twice on a file system without file IDs. An open relative to another folder, an open by file ID (`FILE_OPEN_BY_FILE_ID`) and a name that cannot be read cannot be examined. An open in the game folder is then, in this order: a directory (`FILE_DIRECTORY_FILE`, or the game folder itself; a folder opened without the flag cannot be told from a file before the call), an archive (the last name's extension - from its last `.` that is not its first letter, up to a `:` that starts a stream, so that `x.rpf::$DATA` is the archive - `.rpf` or `.cache` in any case), a write open (asking for `GENERIC_WRITE`, `GENERIC_ALL`, `MAXIMUM_ALLOWED`, `DELETE`, `FILE_WRITE_DATA`, `FILE_APPEND_DATA`, `FILE_WRITE_EA`, `FILE_WRITE_ATTRIBUTES`, `WRITE_DAC` or `WRITE_OWNER`), an exclusive open (its sharing leaves out `FILE_SHARE_READ`), and otherwise an open that gets `FILE_SHARE_WRITE` and `FILE_SHARE_DELETE` added before the call goes on to Windows. Every other open goes on untouched. Windows decides sharing per handle: a new open succeeds only if its access fits the sharing of every handle open on the file and its own sharing allows every such handle's access, so a program that opens a widened file for writing while sharing nothing still gets a sharing violation while the game holds it - the first limit README.md states. The second is Windows' rule for a rename: a file with an open handle, whatever that handle's sharing, cannot be replaced by a classic rename (`FileRenameInformation` with ReplaceIfExists, what `MoveFileEx` makes of `MOVEFILE_REPLACE_EXISTING`), which fails with access denied, while a rename with POSIX semantics (`FileRenameInformationEx` with `FILE_RENAME_POSIX_SEMANTICS`), `ReplaceFile`, a delete followed by a new file and a write in place go through - for a program outside the game's process; inside it, the `NtSetInformationFile` hook below gives a classic replace-rename POSIX semantics. A game folder whose identity cannot be read is a problem, since no relative open - nor a rename's name relative to a folder handle - can then be told to lie in it: `Files in the game folder opened by a relative path are not unlocked this session: the game folder's file ID could not be read (<error>).`
- Every examined open is counted after the call in exactly one of six counts, with atomics, whatever its result: widened, archives, write opens, exclusive opens, directories, not examinable; an open outside the game folder is not counted; every replace-rename into the game folder is counted in exactly one of three counts, whatever its result: given POSIX semantics, made again as the caller made it, passed on with a name too long. A widened open's file is told apart by a hash of its path below the game folder (FNV-1a over its letters, ASCII in lower case, up to a stream) in a fixed table of 16,384 slots that the threads fill without a lock or an allocation, 8,192 files at most; the type of each new file, its extension with the dot in lower case (`(none)` without one), is counted in a fixed table of 15 types in the order they come, a type past the 15th or one that does not fit 8 bytes counting as `others`. The summary is a measurement (section 6.6) whose thread starts with the hooks and waits for an event they set at the first open or rename they count, so that it comes 10 seconds after it, then every minute while the sum of the counts changes, each count read once: `UNLOCK_FILES: in its first 10 seconds, N opens of M files in the game folder other than .rpf and .cache were given write and delete sharing, so those files stay free for other programs; by type: .txt 4, .asi 1, (none) 1, others 1; left as they were: A opens of archives, B write opens, C exclusive opens, D directories, E whose path could not be examined; replace-renames into the game folder: R given POSIX semantics, F made again as the caller made them where the file system refused that, P passed on as made, their names longer than 1024 characters.` - `so far` in place of `in its first 10 seconds` later, `more than M files` once the table of files is full, no types while there are none. Without `DIAGNOSTIC_MODE` no line per open is written.
- With `UNLOCK_FILES`, `NtSetInformationFile` is hooked at the start-up too (`HookExport`), right after `NtCreateFile` and also when that hook could not be made: `UNLOCK_FILES: NtSetInformationFile is hooked - a rename inside the game that replaces a file in the game folder gets POSIX semantics, so it goes through while the game holds that file open.` A hook that cannot be made is a problem of the start-up summary: `The replace-renames into the game folder are not given POSIX semantics this session: NtSetInformationFile could not be hooked (details in TweaksV.log).` With `DIAGNOSTIC_MODE` alone it is not made. The hook passes every information class but the two renames, `FileRenameInformation` (10) and `FileRenameInformationEx` (65), on at once, the class compared and nothing read, and so it passes every call made on a thread inside one of TweaksV's hooks (`t_inside`). A replace-rename - ReplaceIfExists set, or `FILE_RENAME_REPLACE_IF_EXISTS` without `FILE_RENAME_POSIX_SEMANTICS` - is examined on the copy, so that what is examined is what goes to Windows; every other rename goes on as made. Its target lies in the game folder when its name is relative to a folder handle that is the game folder's - told by its identity as for an open, one query, two on a file system without file IDs - and does not start with `\`; when its full name lies below the game folder, compared as an open's; and when it is a bare name - no folder handle, no leading `\`, a rename inside the source's own folder for Windows - whose source lies below the game folder: the source's object name (`NtQueryObject`, `\Device\HarddiskVolume3\...`), one query into a stack buffer of 1024 characters, compared with the game folder's object name read the same way at the start-up, letters in ASCII case - not its final path (`GetFinalPathNameByHandleW`), which would allocate, take locks and ask the mount manager inside the hook, so a source opened by a short 8.3 path goes on as made. A bare name with a `\`, which Windows refuses, a name or a source with a `:` below the game folder - a stream, no file in it - and every target elsewhere go on as made. A replace-rename into the game folder goes to Windows as `FileRenameInformationEx` with `FILE_RENAME_REPLACE_IF_EXISTS`, `FILE_RENAME_POSIX_SEMANTICS` and the caller's other flags (`FILE_RENAME_IGNORE_READONLY_ATTRIBUTE`, say), from the copy, its length 20 bytes and the name's, 24 at least; one whose name has more than 1024 characters is passed on as made. Where Windows answers the rename turned with `STATUS_NOT_IMPLEMENTED`, `STATUS_INVALID_INFO_CLASS`, `STATUS_INVALID_PARAMETER`, `STATUS_INVALID_DEVICE_REQUEST` or `STATUS_NOT_SUPPORTED` - a file system that does not take the class or the flag, a FAT drive, a network share, a Windows older than 10 1607 - the call is made again as the caller made it and its result returned; every other answer, a failure too, is returned as Windows gave it. The test build stands in for such a file system with `TWEAKSV_TEST_NO_RENAME_EX=1` (section 13.1). The game folder's object name is read once before the hook is made, with `NtQueryObject` on the folder; one that cannot be read is a problem, since no rename by a bare name can then be told to lie in it: `Replace-renames in the game folder by a bare name are not given POSIX semantics this session: the game folder's path could not be read (<error>).` With `DIAGNOSTIC_MODE`, after the call (`AfterCall`), each rename turned is a line: `rename #N: <target below the game folder> | <result> | <asked>, <form> -> FileRenameInformationEx, flags 0x... | from <callers>` - the result `ok` or the status, or where the file system refused POSIX semantics `refused (<status>), made again as made: <result>`; asked `FileRenameInformation with ReplaceIfExists` or `FileRenameInformationEx, flags 0x...`; the form `a full name`, `a name relative to the game folder` or `a bare name`, whose target is the source's folder and the name; the callers as an open line's - 20,000 lines at most (`DIAGNOSTIC: 20000 lines of renames turned written - from now on they are only counted.`), the renames counted all the same. Programs outside the game are not touched: their classic replace over a file the game holds still gets access denied, the limit README.md states.

### 11.9 Blips (`InitBlips`)

The game's script `blip_controller` makes the vanilla blips behind a guard: a loop that calls the native that counts the active blips, compares the count with a threshold of its own, 150 on 1.0.1158.16, and while the count is at or above it waits 2000 ms and counts again (PATTERNS.md, "Blips"). The part raises that threshold to `ACTIVE_BLIP_LIMIT` - 150..1997, 1997 being the count's lowest answer with the pool full, so that a higher limit could let the script make a blip into a full pool - in the script's code each time the game places the script, at the start and again at every save load, a new program object each time, as a user of the script programs' hook (section 13.3). `InitBlips` reads the limit and `DIAGNOSTIC_MODE` once, then calls `Scripts::AddUser({ "Blips", before, after }, reason)`: a hook that cannot be made is the part's problem with the module's reason (`blip_controller's threshold is not raised this session: Y-E-H1 was not found.`); a hook made is said, `Each time the game places blip_controller, its guard's threshold is set to 1900 (ACTIVE_BLIP_LIMIT; the game's own: 150).`; in a dry run the call is not redirected and the part sees no program, `DRY_RUN: the natives' resolution call is not redirected, so blip_controller is not looked at - its guard is found and checked on a boot without DRY_RUN.`

`before`, at every placement, on the game's resource placement thread: a program object that cannot be read (`IsReadable`, 0x80 bytes) is logged once and left; one whose hash at +0x58 is not `blip_controller`'s (0x80CFE974, `Scripts::NameHash`) costs that read and nothing more; one with the hash and another name, read with `Scripts::ReadName` within 64 bytes, is logged once (`A script program has the hash of blip_controller, 0x80CFE974, but is named blip_imposter - left as it is (logged once).`). For `blip_controller` itself, its placements counted from 1: its code length 1 byte..16 MB and its native count 1..65536 (the module's bounds), its native table readable, its code's page table and every page readable (`PageLength`); then the whole code is decoded from 0 with the opcode lengths of the game's own table, constants in the part (`kLengthRanges`, checked when TweaksV is compiled to cover 0x00..0x82 once, in order), ENTER 5 bytes and its name's (the byte at +4), SWITCH 2 and 6 per entry (the byte at +1). A byte above 0x82, or an instruction that runs past the code or past its page - SWITCH's count within its page, its entries within the page of ip + 2 - refuses the program (`its code cannot be decoded: the byte 0xA0 at 0x200 is no instruction`), so the bytes inside operands, names and SWITCH tables are never taken for a match. The decode marks every instruction's start in a bitmap, a bit per byte of code, allocated per placement inside a `try` (`there was not enough memory to read its code`), and notes the first CATCH, THROW or CALLINDIRECT.

The guard is tried at every instruction start that is a NATIVE with no argument and one result, in a window of 256 bytes from it (fewer at the code's end), every instruction of the guard on an instruction start in the window and ending in it: the count's NATIVE; any NOPs; the threshold's push, PUSH_CONST_U8 or PUSH_CONST_S16, 1..1997; IGE or ILT, maybe NOT, then JZ - or the fused IGE_JZ or ILT_JZ in their place; the branch's target an instruction start in the window. JZ jumps when what it takes is 0 and a fused jump when its comparison is false, so the branch leaves the guard either while the count is below the threshold - the game's ILT NOT JZ, and IGE JZ or IGE_JZ - or while it is not - ILT JZ, IGE NOT JZ, ILT_JZ: the way out and the body are the branch's target and the instruction after it, in that order or the other. From each, NOPs and jumps (J) are followed within the window, a circle or a step off an instruction start failing the match: the body is a push of 2000 (PUSH_CONST_S16, PUSH_CONST_U24 or PUSH_CONST_U32) and a NATIVE with one argument and no result, WAIT, after which NOPs and jumps lead back to the count; the way out may not lead back into the guard. The two natives' indices (big-endian, at +2 of their NATIVE) lie below the native count and differ. A sequence with the guard's head but not the rest is a miss with its reason, the first of which the problem names when no guard is found (`its guard was not found in its code - the count and a comparison with a threshold are at 0x3FE, but its WAIT calls native 3, which is not below its native count, 3`). Refused, the program left as the game placed it: no guard (`its guard was not found in its code`); a second one (`its guard was found twice in its code, at 0x3FE and 0x800 - which one is meant cannot be told`); a CATCH, THROW or CALLINDIRECT anywhere in the code, whose target is computed while the script runs and could lead into the guard (`its code holds a CATCH, THROW or CALLINDIRECT at 0x..., whose target is computed while the script runs and could lead into its guard at 0x3FE of its code`); a jump (J, JZ and the fused jumps: ip + 3 + their signed 16-bit offset), a CALL (its unsigned 24-bit address) or a SWITCH case (its unsigned 16-bit offset from the entry's end), as the interpreter reads them from anywhere that leads into the bytes from the end of the count's NATIVE through the branch (`a jump at 0x100 leads into its guard at 0x3FE of its code, between 0x402 and 0x408`).

The threshold found: the configured limit already - left, `blip_controller's guard at 0x3FE of its code holds the threshold 1900 already (ACTIVE_BLIP_LIMIT=1900) - nothing to patch (placement 1).`; one other than the game's 150 - left as it is and logged, not a problem, as the heap adjuster leaves a heap another adjuster set (`blip_controller's threshold is not raised (placement 1): its guard at 0x3FE of its code holds 240, not the game's own 150 - left as it is.`); the game's 150 - the rewrite is prepared: the bytes from the end of the count's NATIVE to the branch become NOPs, the new threshold's push right-aligned against the branch - PUSH_CONST_U8 up to 255, PUSH_CONST_S16 above - and the comparison that keeps the polarity, IGE where the branch leaves the guard while the count is below the threshold and ILT where it leaves it otherwise; a fused branch's opcode becomes JZ, its offset and so its target unchanged; nothing after the branch moves - `43 6C 07 0B` for 1900, `00 25 C8 0B` for 200, in the place of the game's `25 96 0C 06`. ### 11.10 WeaponLimits (`InitWeaponInfos`, `InitWeaponComponents`)

### 11.14 RayTracing (`InitRayTracing`)

The game skins every moving object its ray tracing keeps into one global vertex buffer each frame, the output of its `bvh_skinning` compute effect, which the BLAS refits read before the TLASes are built: 4,194,304 vertices of 20 bytes on 1.0.1158.16, 80 MB, made once at the renderer's start, after `DllMain`, by the set-up's call of the buffer maker with the count as an immediate (`T-E-B1`). Each frame's BVH build hands out ranges of it from 0, by a counter per frame slot, and two checks - every moving object's geometry's (`T-E-C1`) and the ropes' (`T-E-C2`) - refuse a range whose end would pass the same immediate: the object then has no ray traced shadow, reflection or occlusion in that frame, and as the order of the objects changes they come and go (PATTERNS.md, "RayTracing"). `DYNAMIC_BVH_VERTICES` under `[RAYTRACING]` is 0, the game's own and the default, or 4,194,304 to 26,843,545 vertices; the settings' range is 0..26843545, so a value above the cap is clamped and reported by them (section 4.1). The cap keeps a raw view of the buffer within 2^27 32-bit elements, far below the 26 bits the ray tracing shaders read an object's first vertex in and the game's 32-bit sizes; a `static_assert` ties it to the setting's maximum. With the key at 0 the part logs `DYNAMIC_BVH_VERTICES=0 - the ray tracing buffer of moving geometry is not raised.` and, without `DIAGNOSTIC_MODE`, looks for nothing and writes nothing.

### 11.15 The parts measured first (`kMeasuredFirst`)

#### 11.15.2 Siren count (`MeasureSirenCount`)

The game lights 20 sirens of a vehicle, `siren1` to `siren20`: its renderer runs over 20 lights, and a model's bone structure names the bones of `siren1` to `siren20` and of their glass by signed bytes, so a model made for more sirens keeps the rest dark and a bone past index 127 cannot be named at all (PATTERNS.md, "Siren count"). With `DIAGNOSTIC_MODE=1` the module looks for `I-E-B1` to `I-E-B4`, once each - each one missing logged by the scanner, the first of them named: `DIAGNOSTIC: the siren count is not measured: I-E-B1 was not found.` - and checks them; every line starts with `DIAGNOSTIC: the siren count is not measured: ` when a check fails. The call at +13 of `I-E-B1`, the renderer's, and the one at +24, the siren settings getter's, whose rel32 lies past the match and is read after `IsReadable`, must lead into the game (`the siren lights' renderer call at RVA ... is not a call into the game (another mod may have hooked it already) (I-E-B1).`, and the same of `the siren settings getter call`), logged as `DIAGNOSTIC: siren lights' renderer call at RVA ... -> RVA ..., siren settings getter call at RVA ... -> RVA ... (I-E-B1)`; `I-E-B2` must lie in the function the renderer's call leads to by the game's unwind data (`RtlLookupFunctionEntry`; `I-E-B2 at RVA ... does not lie in the siren lights' renderer at RVA ...: the game's unwind data puts it in the function at RVA ....`, or `... names no function there.`), logged as `DIAGNOSTIC: bone structure offset at RVA ... holds 0xB0, siren1's bone offset at RVA ... holds 0x99, in the function at RVA ... (unwind data) (I-E-B2)`; `I-E-B3` is logged as `DIAGNOSTIC: siren_glass1's bone offset at RVA ... holds 0xAD (I-E-B3)`; and `I-E-B4`'s match must be a function start by the game's unwind data, as the wrapper calls it - not by the byte before it, which `IsFunctionStart` (section 9) takes for code without unwind data (`find-bone-by-name at RVA ... is not a function start (inside the function at RVA ... (unwind data)) (I-E-B4).`, or `(no unwind data)`), logged as `DIAGNOSTIC: find-bone-by-name at RVA ..., a function start (unwind data), bone count offset at RVA ... holds 0x5E (I-E-B4)`. The four offsets the module reads by - 0xB0, 0x99, 0xAD and 0x5E - are checked against the bytes their patterns pin when TweaksV is compiled (`PatternByte`). With `DRY_RUN` the module logs the line that would redirect the call, `DRY_RUN: would redirect the siren lights' renderer call at RVA ....`, then `... not measured: DRY_RUN - the siren lights' renderer call is not redirected, so nothing is counted.`, and stops. Otherwise it makes the measurement's event, starts its thread (section 6.6, `siren count summary`; `its summary's event could not be made (...).`, `its summary thread could not be started.`) and only then redirects the call (`RedirectCalls`, through a read+execute stub; a call that cannot be redirected - Windows' dynamic code policy, for one - is logged by the patch module and `the siren lights' renderer call at RVA ... could not be redirected (details above).`), so that a measurement that cannot sum up redirects nothing; after a failed redirect the thread waits for a first model that never comes. Nothing of it is reported - the module's lines are under `[SirenSettings]`, the scanner's under `[Scanner]`, a thread that cannot start under `[TweaksV]` (section 6.6) - no problem, no box. A call redirected is announced: `DIAGNOSTIC: the siren lights' renderer call at RVA ... is redirected (I-E-B1): the vehicle models with sirens on, each counted once with its siren bones looked up by name up to siren32, are logged 10 seconds after the first, then every minute while they change.`

The wrapper, `CountedSirenLights`, takes the renderer's nine arguments - the three floats as floats, the stack's five as 64-bit values, so that each slot reaches the renderer as the game's call left it - calls the game's renderer first and returns its rax, then counts, on the game's thread, with no lock, no allocation and nothing that can throw: one lookup of the model info in a fixed table of 1,024 slots, from a Fibonacci hash of its address over 32 slots at most. A free slot is claimed by compare-exchange, so a new model drawn on two threads at once is counted once, and a model that finds neither its slot nor a free one among the 32 counts its pass as not held. On a model's first pass, with the caller's last error kept around it: the hash of its name at +0x18; its bone structure through the two pointers from +0xB0 and the structure's 20 siren and 20 glass bytes; the skeleton data, the skeleton's first field, and its bone count at +0x5E - every pointer through `IsReadable`, the first that cannot be read making it a model that could not be read - then, unless the bone count is 0, 64 calls of the game's find-bone-by-name, `siren1` to `siren32` and `siren_glass1` to `siren_glass32` (names made when TweaksV is compiled), each guarded as `CopyMemorySafely` guards a read, since no pattern pins what the renderer's 7th argument holds: an access violation in it is caught, and the model is one that could not be read, looked at no more; and for each bone found among the first 20 its index at +0x42 - one its bone structure does not name counts as lost past bone 127 when that index is past 127, and below 128 as a disagreement of its own. The first model counted sets the event. The summary (section 6.6), 10 seconds after it and then every minute while the models counted change, walks the table: `DIAGNOSTIC: 4 vehicle models with sirens seen in 800 passes of the siren lights' renderer - the most sirens a model's bone structure names: 20 of 20 (model 0x79FBB0C5); 1 with siren bones past siren20, which the game never lights; 1 losing siren bones past bone 127, which a bone structure cannot name; 0 that could not be read.` - the model of the most sirens the one with the lower hash of two, `none read` in its place when no model could be read, and `; the table full, N passes of models it could not hold not counted` before the end when there are such passes. Then a line, once, for each model the limit binds, that could not be read, or whose bones by name and bone structure disagree - which says the measurement is not right for it - its numbers in pairs, the sirens' first: `DIAGNOSTIC: vehicle model 0xA1B2C3D4, 100 bones - siren and glass bones by name: 32 and 32, up to siren32 and siren_glass32; named by its bone structure: 20 and 20; past siren20, never lit: 12 and 12.`, with `; lost past bone 127, found by name but not named by its bone structure: 2 and 0 (the highest bone 129)`, `; found by name below bone 128 but not named by its bone structure: 1 and 0`, `; named by its bone structure but not found by name: 0 and 1` and `; found by name at another bone than its bone structure names: 1 and 0` where they apply; `DIAGNOSTIC: vehicle model 0x0BAD0001 could not be read: its bone structure (the model info's +0xB0).`, `... its skeleton data (the renderer's 7th argument, its first field).` or `... find-bone-by-name faulted on its skeleton data (an access violation).` The lines per model are bounded by the table's 1,024 slots, below `kMaxLinesPerKind` (a `static_assert`), so they need no cap.

## 12. The rules every part follows

- **Nothing is written before everything is found and checked.** Every site is found by pattern, every instruction's bytes are the expected ones, every address inside the game, every value plausible and consistent; the first thing not as expected ends the part's job with nothing changed.
- **All or nothing.** A job's writes go in one `WriteCode` or `RedirectCalls`: every page made writable first, every page given its own protection back, on an exception too; a part either does its whole job or leaves the game as it was. Hooks of one group are created and switched on together or removed again. The writes in `DllMain` happen while the game is still single-threaded; RageOpenV's start-up writes its few bytes - the cache check's `C3 90`, the console's NOPs, the five `E8 rel32` - on the game's thread at the first time request without freezing the other threads, as MinHook does for the hooks: an accepted window, since no other thread runs that code then (NOTES.md, T-FREEZE). The Blips part writes into a script program on the game's resource placement thread, after `DllMain`, but before the game enters the program in its registry of programs, where no script thread can run it (section 13.3).
- **What another mod has already changed, TweaksV does not change again.** A heap another adjuster set, a cache check already skipped, a function already hooked (hooked on top, chained through) are left and logged; an array already moved, a call already redirected, a pattern that matches more often than it must are refused with the reason, because what TweaksV would write over cannot be known. The conflict check switches a part off entirely when its old plugin is installed, or a plugin that does its job too and stays (section 7).
- **Never silent.** Every job not done is a `PROBLEM` line in the log with the reason and an item of the start-up summary, which is a message box with `ERROR_POPUP=1`; a part that stops working after the start-up gets a box of its own. A switch that is off is logged in one line. DirectStorage's job is its `NtCreateFile` and `NtSetInformationFile` hooks: one that cannot be made is a problem of the start-up summary. A job whose effect comes later is checked for it: RageOpenV's start-up check reports a start-up that never ran (section 11.6), and the static bounds' check a pool size the game did not ask for in the 60 seconds after the session's start (section 11.13); the files a guard of WeaponLimits refuses are reported with the part's box (section 11.10). An aid that cannot be set up - the console, DirectStorage's call logging (its factory and `OpenFile` hooks and the checks that the game asks for its factory), a measurement whose thread cannot start (section 6.6), the `UNLOCK_FILES` summary's among them, RayTracing's counting stubs (section 11.14) and the static bounds' check (section 11.13) - is logged, not reported (NOTES.md, T-DIAG). `DRY_RUN` and `DIAGNOSTIC_MODE` work the same for every part, with two exceptions: with `DIAGNOSTIC_MODE=1` the box streamer refuses its whole job when a tree-search call cannot be redirected, because the measurement is the reason the switch is on (section 11.4); and with `DRY_RUN=1` the Blips part checks its hook's sites but never sees `blip_controller`, which reaches it only through the hook a dry run does not make (section 11.9). The parts measured first are aids as a whole (section 11.15): without `DIAGNOSTIC_MODE=1` they look for nothing, a failure of one is logged and not reported, and `DRY_RUN` changes nothing in them but the siren count's measurement, which then redirects nothing.
- **Everything read is bounded and checked.** INI values are trimmed, limited to 255 characters, parsed and clamped; the mods list has limits on entries, depth and path length; paths from the game are read with a length limit, paths from DirectStorage copied with a length limit and a guard against unreadable memory, and the name of every `NtCreateFile` call read within its own length under the same guard, and every rename's buffer within the length its caller gives, its name copied only when it has 1024 characters at most; the entry table of an archive is walked only when its count is plausible, and the check for packs made for GTA V Legacy reads each archive's header, entry table and names within its bounds - 1,048,576 entries, the table inside its archive, 65,792 bytes of names, 8 levels of nesting, 4,096 archives and 64 MB per pack, 1 GB in all (section 11.6); the scanner reads the PE header and the section table only where they lie inside the image, and unwind data is asked of Windows (`RtlLookupFunctionEntry`); the measurements and the guards of WeaponLimits read the game's data only after `IsReadable` or through `CopyMemorySafely`, within bounds of their own (sections 11.10 to 11.15); the log cuts its lines and its file.
- **Nothing throws into the game.** Every hook puts what can throw - a log line, a table walk - inside a `try`, and so do the measurement threads, the two threads of `TweaksVSummary`, the static bounds check's thread and the thread of the check for packs made for GTA V Legacy, whose start never throws into RageOpenV's start-up; a lock is never left taken by an exception (`TweaksVLock.h`), nor a page of the game's code writable (the guard in `WriteCode`). The DirectStorage hooks, RageOpenV's ParseHeader hook and its OpenBulk hooks' lines, the script programs' hook around its users' work (section 13.3), the guards of WeaponLimits, which refuse a file without calling the game's loader (section 11.10), and the static bounds pool's size function, which calls the game's lookup first (section 11.13), keep the game's last error; the other hooks call the game's function last, so the game's own error stands. `DllMain` catches everything on attach and returns `TRUE`.
- **Nothing per frame beyond the game's own work.** The hooks on hot paths (the file functions, the tree searches, DirectStorage's `NtCreateFile`, which every file open of the game passes) do one path spelling and one hash lookup, one count with atomics, or one bounded comparison of the open's name with the game folder and its counts with atomics - no allocation, no lock of TweaksV's, no file system call, but for one query of a folder's identity per open relative to a folder handle (section 11.8); DirectStorage's `NtSetInformationFile` hook compares the class of every call and reads nothing more of one that is not a rename, and a replace-rename costs a copy of its name on the stack and, for a name relative to a folder handle or a bare name, one query of Windows; the `DIAGNOSTIC_MODE` check costs one comparison, and with it on the log lines are capped (below); the measurements are read once a minute by threads of their own; the siren count's measurement, with `DIAGNOSTIC_MODE=1` only, adds to the game's call that draws a vehicle's sirens one lookup in a fixed table of the vehicle models seen, the model's bone lookups only on its first pass (section 11.15.2); RayTracing's, with `DIAGNOSTIC_MODE=1` only, adds a few instructions to each object the full ray tracing buffer refuses - none while the buffer fits - and its sampling thread reads three dwords every 50 ms (section 11.14); the guards of WeaponLimits cost a bounded check per file the game loads (section 11.10).
- **Memory TweaksV adds is never writable and executable at once.** The moved arrays are read/write data; the call stubs are written once and then read+execute, and so are RayTracing's counting stubs, whose counters lie on a page of their own, read/write (section 11.14); MinHook's trampolines are the one exception, accepted (NOTES.md, T-HARDEN). The build carries ASLR with high entropy, DEP, Control Flow Guard and CET compatibility, statically linked (section 15).
- **Per-event output is capped.** Every kind of line that can come without bound - file requests, files served, archive headers, OPEN archives left as they are, mods files that cannot be opened, folders of the mods folder that cannot be read, the packs the check for packs made for GTA V Legacy names or reads, the opens inside the game folder, DirectStorage's `OpenFile` calls and the renames it turns, the `weapons.meta` and `weaponcomponents.meta` files the WeaponLimits part logs, the ped props past 255 - stops after 20,000 lines of its kind (`kMaxLinesPerKind`, section 6.6; the cap lines are in section 6.3); the events are then only counted, with a summary every minute where `DIAGNOSTIC_MODE` gives one, so no boot fills the 64 MB log. The tables behind a summary are bounded too: DirectStorage's open summary takes 100,000 entries per table, its `UNLOCK_FILES` summary 8,192 files and 15 types.
- **One wording** (section 6.3) and one log tag per part, the feature name.

### 13.2 The code dump (`TweaksVDump`)

`StartCodeDump()` takes a copy of the game as it is before any part changes it, and a thread saves it as `GameCode-start.bin`, waits the seconds asked for, takes a second copy and saves it as `GameCode-later.bin`, both in `%LOCALAPPDATA%\TweaksV` through the own-file checks, never in the game folder. A copy holds the PE headers and every section that is not writable - the code, the constants, the function table - and a writable one only when it is also executable; the plain data sections, which can hold the player's data, are never saved; bytes that cannot be read are saved as zeros and counted. The file (format version 1, little-endian): a `DumpHeader` (`magic` "TWKVDUMP", `formatVersion` 1, `sectionCount`, `imageBase`, `imageSize`, `timeDateStamp`, `secondsAfterStart`, `reserved`; 40 bytes), one `DumpSection` per section (`name` as in the section table, "HEADERS" for the headers; `rva`, `size`, `characteristics`, `unreadable`, `fileOffset`; 32 bytes), then the bytes of each section at its `fileOffset`. The log says what was saved: `TEST BUILD: GameCode-start.bin saved, the game as it was 0 s after TweaksV started, before anything was patched: 50.3 MB in <folder> - sections HEADERS .text ...; none unreadable; not saved (the game writes to them): .data ...`. This is how patterns are found after a game update: a dump of the running game is rebuilt as a PE (the headers and the saved sections at their offsets, `.data` as zeros) and analysed with Ghidra's headless analyser, the `.pdata` table giving the functions (PATTERNS.md, "When Game Updates", item 3).

### 13.3 The script programs (`TweaksVScripts`) and their copy (`TEST_DUMP_SCRIPT`)

A script program is one of the game's compiled scripts - `blip_controller` and the others its archives store, encrypted - as the game holds it in memory: its code and its strings in pages of 16 KB, its table of natives (the game's functions it calls) and its name (PATTERNS.md, "Script programs"). The game makes one in the program's resource constructor whenever it streams the script in, on its resource placement thread; the constructor calls the game's function that resolves the natives (the call at +3 of `Y-E-H1`) and only afterwards enters the program in its registry of programs, where every script thread looks its program up each time it runs, so no script thread can run a program while that call is under way.

`TweaksVScripts` owns the one redirect of that call, for every part that works on a script program. A user is a `Scripts::User { tag, before, after }`: `before(program, placed)` runs for every program the game places, before its natives are resolved - the native table still holds their hashes - with how many programs the hook has seen so far, this one included, and what it returns comes back to `after(program, resolved, context)`, which runs once the game's function has returned, with its byte (1 when every native was found). `Scripts::AddUser(user, reason)`, from `DllMain` only, puts the user into a fixed table of four - no allocation and no lock on the game's thread, the count published after the entry - and the first user makes the hook: `Y-E-H1`, `Y-E-N1` and `Y-E-I1` are looked for, each one missing logged by the scanner and the first of them named in the reason (`Y-E-H1 was not found.`); the call at +3 must lead into the game (`the natives' resolution call at RVA ... is not a call into the game (another mod may have hooked it already).`); and `RedirectCalls` sends it through a call stub to the module's `ResolveHook` (with `DRY_RUN`, `DRY_RUN: would redirect the natives' resolution call at RVA ...` and nothing else; a write that fails gives `the game code could not be changed (details in TweaksV.log).`). `DIAGNOSTIC_MODE` logs the three sites under the user's tag: `DIAGNOSTIC: natives' resolution call at RVA ... -> RVA ..., strings' length offset at RVA ... holds 0x70 (Y-E-H1)`, `DIAGNOSTIC: code length offset at RVA ... holds 0x1C, native table offset at RVA ... holds 0x40 (Y-E-N1)` and `DIAGNOSTIC: code page table offset at RVA ... holds 0x10 (Y-E-I1)`. A hook made is logged, `The natives' resolution call at RVA ... is redirected: every script program the game places passes TweaksV, before and after the game resolves its natives.` The outcome is kept: a later user joins a hook that is made, and gets the first user's reason when it could not be made, which each user reports as its own problem. `ResolveHook` calls every user's `before`, then the game's function, then every user's `after`, each user inside a `try`, with the game's last error kept around their work, and returns the game's byte. The module gives its users the layout too: the fields as named constants (`kCodePagesOffset` 0x10, `kCodeLengthOffset` 0x1C, `kNativeCountOffset` 0x2C, `kNativesOffset` 0x40, `kNameHashOffset` 0x58, `kNameOffset` 0x60, `kStringPagesOffset` 0x68, `kStringLengthOffset` 0x70, `kProgramSize` 0x80), the four a pattern pins checked when TweaksV is compiled against the byte the pattern holds there (`PatternByte`, section 4.2) - `Y-E-H1` pins `kStringLengthOffset` at +18, in the constructor's loop over the strings' pages after the call; the page rule (`kPageSize`, `PageCount`, `PageLength`), its rounding, `kPageSize - 1`, pinned by `Y-E-H1` at +10 the same way; the bounds a program's fields are read within (`kMaxLength`, 16 MB for the code and for the strings - a call's target in the code is 24 bits - and `kMaxNatives`, 65536 - a native's index is 16 bits); `Field`, a field of a program or of a table it points to, read once `IsReadable` has said so; `ReadName`, the name read within `kNameRead`, 64 bytes, a memory page at a time and only where it can be read, and `Printable` for a log line; and the game's hash of a script's name (`NameHash`, checked against `blip_controller`'s 0x80CFE974 when TweaksV is compiled).

`TEST_DUMP_SCRIPT=<name>` (test builds) is its first user, started by `StartScriptDump()` at step 7 of the start-up, after `StartCodeDump()`, under the tag `TweaksV`; the Blips part is its second, joining at step 8 (section 11.9), so the switch's copy shows a program as the game placed it, before the part writes to it; the StaticBounds part joins after them, for the session's start (section 11.13), and makes the hook itself while `TweaksV.ini` switches Blips off, no plugin that does Blips' job is installed and the switch is not set. The name is 1 to 63 letters, digits and `_`, compared without case; another value is reported (`TweaksV.ini: [TWEAKSV] TEST_DUMP_SCRIPT=../x is not a script's name of 1 to 63 letters, digits and _ - no script program is saved.`), and so are a `LOCALAPPDATA` that is not set (`TEST_DUMP_SCRIPT: LOCALAPPDATA is not set - no script program is saved.`) and a hook that cannot be made (`TEST_DUMP_SCRIPT: the script program blip_controller is not saved this session: Y-E-H1 was not found.`), and nothing is hooked. Otherwise the log says what the switch waits for, `TEST BUILD: TEST_DUMP_SCRIPT=blip_controller: the script program blip_controller (hash 0x80CFE974) is saved each time the game places it, at most 16 times, as Script-blip_controller-<n>.bin in <folder>.` - with `DRY_RUN`, `TEST BUILD: TEST_DUMP_SCRIPT=blip_controller: DRY_RUN - the call is not redirected, so no script program is saved.`

At each placement, on the game's thread, every read of the game's memory is checked with `IsReadable` first - the name a memory page at a time, within 64 bytes. The first program of all is logged, whatever its name - the line that proves the hook runs: `TEST BUILD: TEST_DUMP_SCRIPT: the first script program the game placed is <name> (hash 0x...), on thread N - the hook runs.` A program whose hash at +0x58 is the name's and whose name is that name is copied; one with only one of the two is logged once (`TEST BUILD: TEST_DUMP_SCRIPT: a script program has the hash of blip_controller, 0x80CFE974, but is named <name> - it is not saved (logged once).`) and not copied. The bounds, the module's: the code and the strings 16 MB each and 65536 natives; a program beyond them is a problem (`TEST_DUMP_SCRIPT: Script-blip_controller-3.bin was not saved: its code length, 16777217 bytes, is beyond 16 MB.`, `... its native count, 65537, is beyond 65536.`) and not copied. `before` allocates the file and copies the native table while it holds the hashes; `after` copies the program object, the code page after page, the table as the game left it and the strings, a page that cannot be read as zeros, counted, and writes the file right there, on the placement thread, through `OpenOwnFile` in `%LOCALAPPDATA%\TweaksV` (`FileFolder::Own`; the folder made if need be, a file of that name from an earlier session replaced), never in the game folder. At most 16 copies a session: the 17th placement logs `TEST BUILD: 16 copies of blip_controller saved - from now on its placements are only counted.` once. Memory that cannot be had and a file that cannot be written are problems (`TEST_DUMP_SCRIPT: Script-blip_controller-1.bin was not saved: it is a hard link: ...`), which after the start-up summary get a box of their own (section 6.4). Each copy saved is logged: `TEST BUILD: Script-blip_controller-1.bin saved in <folder>: blip_controller placed the 1st time, as the game's 312th script program, on thread N - code 16675 bytes in 2 pages, 245 natives, every one resolved, strings 496 bytes; none unreadable.`

The file, `Script-<name>-<n>.bin`, the name in lower case and n counting this program's placements from 1 (format version 1, little-endian; a research reader is written against it, so a change of its layout needs a new format version): a `ScriptDumpHeader` of 176 bytes (`TweaksVDump.h`, its size checked by a `static_assert`) - `magic` "TWKVSCRP", `formatVersion` 1, `headerSize` 176, `name` (64 bytes: the program's name as the game holds it, zero-padded), `nameHash`, `codeLength`, `nativeCount`, `stringLength` (the program's fields at +0x58, +0x1C, +0x2C and +0x70), `placement`, `threadId` (the thread that placed it), `programsPlaced` (every program the hook saw so far, this one included), `resolved` (the game's byte), 3 bytes reserved, `imageBase`, `imageSize`, `timeDateStamp` (where the game was, its SizeOfImage and its PE timestamp - the game build), `unreadable` (the bytes saved as zeros), a dword reserved, and the offsets of the five blocks that follow in this order: `programOffset` (the program object's first 0x80 bytes, as they are), `codeOffset` (`codeLength` bytes, page after page), `nativesBeforeOffset` (`nativeCount` x 8: the table before the game's resolution - the hashes), `nativesAfterOffset` (the same after it - the handlers' addresses, as they are) and `stringsOffset` (`stringLength` bytes, page after page). The reserved fields are 0.

## 14. The tests

### 14.1 The harness

`test\` holds everything, loose in one folder: `run_all.sh` builds and runs every suite from Git Bash and deletes its intermediates (its Release build replaces `x64\Release\TweaksV.asi`); `common.sh` has the helpers; `build_tweaksv.cmd` builds TweaksV's Release and test builds; `build.cmd` builds the fake programs into `object\TestRun`, with warnings as errors (`/WX`); `vsenv.cmd` finds Visual Studio with vswhere; `deps.cmd`, `headers.cmd` and `junction.cmd` are the integration suite's helpers (a module's imports, the PE headers for the mitigations, a junction made and removed - the rageopenv suite makes one too); the fake programs are `fake_game.cpp`, `fake_game_full.cpp`, `fake_game_rov.cpp`, `fake_game_version.rc`, `fake_dstorage.cpp` and `fake_renamer.cpp`; `base.ini` is the file the game suites start from (layout 4 with `HEAP_SIZE=1024` and `PACKFILEARRAY_SIZE=12000`, two values that are not the defaults, which the part suites and the integration suite assert - `heap: 1024 MB` - and which prove the file is read), `expected_default.ini` the default file of section 5.4, `layout1.ini` the 1.6.0 default for the 1.x-file scenarios. ## 15. Building and releasing

`source\TweaksV.vcxproj` is a plain Visual Studio project, no generated build system: C++20, `/W4` with warnings as errors in spirit (none is tolerated), the C runtime linked statically (`/MT`, `/MTd` in Debug: players need no redistributable), Control Flow Guard with its EH continuation metadata and CET compatibility set in the project (`ControlFlowGuard`, `GuardEHContMetadata`, `CETCompat`); ASLR with high entropy and DEP are the x64 linker's defaults, and the integration suite checks all four on the binary. Its `TweaksVVersionMajor`, `Minor` and `Patch` properties are the version (2.6.0); the `TweaksVBuildInfo` target writes `BuildInfo.h` into the intermediate folder before every build, with `TWEAKSV_VERSION`, its three numbers and `TWEAKSV_GIT_HASH` from `git rev-parse --short HEAD` when the folder is a repository, `-dirty` appended while the tree has uncommitted changes. Four builds matter: Release (`x64\Release\TweaksV.asi` and `TweaksV.pdb`, `object\Release`), Debug (`x64\Debug`, `object\Debug`), the test build (`-p:TweaksVTestBuild=true`, `object\Test\Release`) and the analysis build (`-p:TweaksVAnalyze=true`, `/analyze`, `object\Analyze\Release`); all four must build from scratch (`-t:Rebuild`: an incremental build shows no warnings for files it does not recompile) without a warning before a build reaches me, and `bash test/run_all.sh` must be green; `object\Analyze` is deleted afterwards, as `run_all.sh` deletes `object\Test`, `object\TestRun` and `object\TestTemp` itself. New source files get CRLF line endings; git normalizes every text file to LF, and `.sh` files and `test\*.ini` stay LF (`.gitattributes`). MinHook builds at `/W3`, unchanged, from `vendor\MinHook`. `version.rc` fills the file's version resource from `BuildInfo.h`, with the copyright string `Copyright (C) dachdecker369. Licensed under GPL-3.0-only - see LICENSE.`

A release is a tag `major.minor.patch` on the commit I booted, and a zip with exactly five files, for this version and every later one: `TweaksV.asi`, `LICENSE`, `THIRD_PARTY_NOTICES.md`, `CREDITS.md` and `README.md` - nothing else; the `.pdb` stays with the build. The release notes name the tag and link the repository, and `THIRD_PARTY_NOTICES.md` and `README.md`, which ship in the zip, name the repository too, so the Corresponding Source is one step from the binary wherever the zip goes (GPL-3.0, section 6d). The order: version in the project file, a local commit in the style of the earlier `TweaksV 1.x.y` commits, Release rebuilt from it so the header carries that commit, my boots (with `DIAGNOSTIC_MODE=1` when patterns changed, with my map mods for anything that streams), then, with a clean log, push and tag: an annotated tag named and messaged with the plain version, `main` and the tag pushed together.

## 16. Extending TweaksV

- **A new setting:** one entry in `kSettings` (section 4.1) in its section's place, with its comment for the default file - its `KEY=default` short of the comment column - a named reference, a row in README's table, and `expected_default.ini` with the new default file. `IniKeyCount()`'s `static_assert` names the count (40) and fails until it is updated: a new key in the file means a new layout number (`kIniLayoutVersion`), and the suites pin that number in `run_ini_default.sh` (the header line, the `VERSION`-alone file and its 39 keys added back, the carried layout-2 and layout-3 files, the newer-layout line), in `base.ini` and `expected_default.ini`, and the keys of one section in `run_directstorage.sh`. An existing file of an older layout, from `kIniFirstLayout` on, is carried forward at its next start - its missing keys added, then this layout's `VERSION` written back (section 5.3) - so a new layout needs nothing more in the code. The 1.x rule stays as it is (a file without `VERSION`).
- **A new pattern:** one entry in `kPatterns` with a new label in its part's group, and the row in PATTERNS.md with the same bytes, the offset and what the match holds; the code names it as `Pattern("label")` once. The `patterns` suite fails until both agree. After a game update the same: the table and PATTERNS.md change together, and `DIAGNOSTIC_MODE=1` with `DRY_RUN=1`, `CONSOLE=1` and every part on shows that every pattern matches as often as it must (`D-E-L12` seven times).
- **A plugin that does a part's job:** an old one TweaksV replaces is its file name in `oldPlugins` of each part whose job it does; one that stays installed is a `PeerPlugin` constant in `TweaksVFeatures.cpp`, its file and what it is, named in `peerPlugins` of each such part (the array grows when a part gets a second one), with a comment that says why it stays and what clashes. Either kind gets its scenarios in the integration suite, its row in section 4.3 and its name in README's "Testing" step 2.
- **A new part:** a section in `kSections` and `kSettings` (the layout rule above applies), a feature in `kFeatures` in the order of `kSections` (a `static_assert` checks it) with its old plugins, its plugins that stay and `Init<Part>()`, one file `TweaksV<Part>.cpp` with its header comment, its tag and its credits, listed with its header in `TweaksV.vcxproj` and `TweaksV.vcxproj.filters` (the project lists every file by name), patterns in the table, a suite `test\run_<part>.sh` with the sites added to the fake game and its name in `run_all.sh`'s list of suites, a section and the key rows in README, a bullet in NOTES and the new check count there, a section 11.x here, and the project the part derives from or takes its idea from in CREDITS.md (and in THIRD_PARTY_NOTICES.md where the part carries its code). The part finds and checks everything first, writes through `WriteCode` or `RedirectCalls`, hooks through `HookFunctions`, reports through `ReportFailure` with its job's wording, logs in the wording of section 6.3, and runs a measurement, if it has one, through `StartMeasurement` (section 6.6).
- **A limit measured first,** before its part is built (section 11.15): a module `TweaksV<Limit>.cpp` and `.h` with its header comment, its part's tag and `Measure<Limit>()`, an entry in `kMeasuredFirst` in the order of 11.15, its two files in `TweaksV.vcxproj` and `.vcxproj.filters`, its patterns in its part's group of the table, a suite `test\run_<limit>.sh` with its sites in the fake game and its name in `run_all.sh`'s list, its subsection of 11.15 and its rows here in 2 and 14.2, its section in PATTERNS.md, its paragraph in README's "Measured first" and its line in NOTES. It finds and checks everything its writing half will, logs in the wording of section 6.3, measures through `StartMeasurement` and writes nothing, all with `DIAGNOSTIC_MODE=1` only. Once its part is built, the limit leaves `kMeasuredFirst` and its module becomes the part's.
- **A new array part:** a `RelocationSpec` with its anchors (section 10.1), `FindRelocation` then `ApplyRelocation`; what the core cannot express stays in the part and reads `RelocationPlan::matches`.
- **A part that works on a script program**, as the Blips part does (section 11.9): it registers with `TweaksVScripts` - `Scripts::AddUser` from its `Init<Part>()`, in `DllMain` - reports the reason it gets back as its own problem when the hook is not there, and does its work in its `before` or `after` on the game's placement thread, reading the program by the module's offsets and page rule, every read through `IsReadable`, nothing thrown, no allocation it can do without (section 13.3); a pattern of its own goes in a group of its own in the table (the Blips part's `L`), and the module's table of users has room for four.
- **A fork or a pull request** keeps the license (GPL-3.0-only), CREDITS.md and THIRD_PARTY_NOTICES.md, which must accompany every copy, and the notices' four pieces of code (the console opener, the pattern parser, the free-memory search adapted from MinHook's `buffer.c` and the StaticBounds part adapted from the Static Bounds Limit Adjuster) credited as they are; keeps the parts their own code, as 2.0.0 made them, and carries no code of the projects that are idea only (CREDITS.md names them); keeps the suites green with the count updated in NOTES.md; and keeps the documents true: PATTERNS.md for every game fact, NOTES.md for what a part does, this file for how it does it, README.md for the player.
